RustShare Documentation

Modern, self-hosted file-sharing and sync platform built for technical teams and security-conscious organizations.

Public Preview / late-MVP Status

RustShare is currently in a late-MVP / pre-release state. The core web sharing capabilities, asynchronous replication, and operator recovery tools are fully implemented and highly stable. Active desktop and mobile client features are in progress or prototype phases. We are actively refining the platform for production readiness.

Everything is a File.

RustShare is designed around a single, uncompromising philosophy: "Everything is a File."

In most modern collaboration suites, organization memory is scattered. Notes live in one SaaS app, project boards in another, meeting notes are lost in calendars, and raw files sit in cloud drives. RustShare consolidates these paradigms. Whether it is a raw technical artifact, a markdown document, a collaborative decision, a meeting transcript, or a Kanban board record—it is represented and stored natively as a versioned, secure file. This guarantees that your organization's entire cognitive memory remains traceable, searchable, auditable, and self-hosted.

Core Value Proposition

  • Durable Infrastructure: Built from the ground up for technical teams, utilizing standard S3-compatible object storage as the primary storage layer.
  • Absolute Control: Open-source, private-cloud first, and easy to self-host. No hidden third-party telemetry, no cloud locking.
  • Permission Clarity: Sharing model is designed to be fully understandable, auditable, and testable. No implicit background authorization logic.
  • Traceable Auditability: Detailed access logging and state validation for critical tenant and share actions.
  • Zero-PostgreSQL Profile: Supports a highly optimized standalone runtime profile where metadata is stored directly inside object storage JSON structures, removing SQL database requirements.
  • AI-Ready Bounding: Designed to facilitate future semantic and indexing AI layers, while strictly respecting ACL and user scopes.

Getting Started

Set up RustShare and get it running locally on your machine in under five minutes.

Prerequisites

  • Docker: Engine version 24.0+ or Docker Desktop
  • Docker Compose: V2 is required
  • Hardware Resources: A minimum of 4 GB RAM allocated to Docker
  • Network Ports: Ports 80 and 443 free on your local host (unless overrides are configured)

Quick Start

Copy and run the following commands in your terminal to clone the repository, generate initial environment variables, and bootstrap the container stack:

git clone https://github.com/kubedoio/rustshare.git
cd rustshare
cp .env.example .env
./scripts/pre-flight.sh
docker compose up -d

What Just Happened

Running the quick start starts four core Docker containers that comprise the complete local stack:

Container Name Service Purpose Default Ports
postgres Metadata authority, session logs, and user identity store 5432 (internal only)
rustfs Primary S3-compatible local object storage (content + JSON metadata) 9000 / 9001
backend High-performance Axum Rust API + SvelteKit Single Page App runner 8080 (internal only)
nginx Edge reverse proxy and local request dispatcher 80 (binds to host)
Docker Build Details

The RustShare backend container uses a highly efficient, multi-stage Docker build pipeline. Node.js compiles the SvelteKit frontend as a static single-page bundle, which is then compiled and embedded directly into the final lightweight scratch Rust runtime container.

First-Time Login & Verification

  1. Open your browser and navigate to http://localhost.
  2. Retrieve generated credentials: If you ran ./scripts/pre-flight.sh, high-entropy random passwords were automatically generated. Retrieve the bootstrapped administrator password by querying your running container logs: 
    docker logs rustshare-backend-1 | grep "Bootstrap admin password"
    Alternatively, inspect the RUSTSHARE_ADMIN_PASSWORD and RUSTSHARE_DEMO_VIEWER_PASSWORD values written to your local .env file.
  3. Sign in as administrator.
  4. Run the post-launch validation suite: Confirm that the API, database connectivity, replication channels, and S3 credentials are in full working order: 
    ./scripts/final-launch-smoke.sh

Core Concepts

Understanding the unified design paradigms that shape RustShare and differentiate it from general-purpose cloud storage providers.

Everything is a File

RustShare consolidates team knowledge by treating all objects natively as version-controlled files inside explicit namespaces. By making files the universal primitive, we achieve massive architectural simplifications: version history, permission control, backup policies, and full audit trails are handled uniformly across all collaboration models.

The Product model

  • Workspaces: Logical multi-tenant partitions. A Workspace binds a specific set of users, security groups, and storage policies to isolated content hierarchies.
  • Files and Folders: Traditional hierarchical directory structure. Supports instant upload, download, renaming, deep copy, soft trash deletion, and immutable version restore.
  • Notes: Rich collaborative markdown documents. Notes are saved automatically to the active folder in real-time, can embed attachments, and can be shared externally with a single click.
  • Attachments: Durable metadata linking static assets, spreadsheets, and binary files directly to text-based documents or meeting logs.
  • Meetings: Structured markdown logs for capturing meeting agendas, participant lists, and actionable tasks. They are written to designated folders and linked to relevant project paths.
  • Decisions: Architectural Decision Records (ADRs) and business decisions stored as versioned documents requiring explicit member signatures and approval workflows.
  • Kanban Records: Lightweight task tracking cards grouped in boards. Unlike database-siloed project tools, each Kanban board is represented as an plain JSON schema folder, making tasks fully traceable and auditable.
  • Sharing Model: Decoupled into Internal Sharing (targeting specific workspace users or groups with granular Viewer/Editor roles) and Public Links (allowing anonymous access, optional passwords, expiration caps, and upload-only folder-drops).
  • Explicit Permissions: Permissions are never implicit. Effective access is computed dynamically based on parent directory grants. Revoked states are applied instantly.
  • Auditability: Detailed system-wide append logs tracking exactly who read, modified, downloaded, or shared an asset.
  • Future Permission-Aware AI: A foundational design principle that guarantees that when a semantic indexer or LLM queries your files, it cannot bypass the user's explicit ACL settings. You only see AI responses generated from files you have access to.

System Architecture

A look under the hood of RustShare's hybrid, service-oriented infrastructure.

Product Implementation vs. Intended Direction

This technical section explicitly distinguishes between what is implemented and functional inside the current codebase versus the long-term architectural goals of the project.

High-Level Technical Stack

RustShare uses a decoupled, three-tier structure designed to maximize throughput, minimize memory usage, and ensure complete container isolation:

  • Rust Backend: Built using Axum for the REST/WebSocket router, sqlx for compiled-checked SQL queries, and the tokio runtime. It handles OIDC logic, JWT generation, file operations, replication claims, and permission processing.
  • Svelte Frontend: Written in Svelte 5 utilizing SvelteKit. It operates as a high-performance Single Page Application (SPA), caching UI layouts and establishing active WebSocket connections for realtime toast notifications.
  • Storage Orchestrator: Uses S3-compatible storage layers (such as AWS S3, Cloudflare R2, MinIO, or the default local RustFS) to store both immutable binary content and structured JSON metadata.

Major Update: Zero-PostgreSQL Profile (Implemented)

Historically, RustShare required PostgreSQL as its relational database core. On March 27, 2026, the team completed the Zero-PostgreSQL Refactor.

We now support a Standalone (single-node) execution profile that completely bypasses Postgres. In this profile, RustFS acts as the canonical store of record. User profiles, system configuration, directory structures, and permission grants are stored natively in the S3 backend as encrypted, hierarchical JSON documents, with an in-memory caching layer handling fast read queries. This eliminates runtime overhead, significantly simplifying deployment.

For large-scale, multi-node setups, the Distributed Profile pairs the object storage with Redis to manage distributed locks, job claims, and rate limits.

Future Technical Integrations

  • RustChat Integration: Deep, native linking with RustChat platforms. The integration will utilize a shared OIDC identity layer and bounded API contracts to fetch permission-checked file references inside chats, preventing the sharing of database backends.
  • Permission-Aware AI Layer: Planned event-driven projections that index file content changes in the background, feeding updates into vector DBs. The retrieval-augmented generation (RAG) system checks the exact ACL of the requesting user at query execution, preventing security bypasses.

Deployment Guide

Instructions for taking RustShare from a local quickstart to a production-hardened self-hosted cluster.

Production Deployment

For production deployments, combine the base Docker Compose manifest with the production-hardening overrides:

docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

Production Hardening Checklist

  1. High-Entropy Secrets: Ensure you generate strong keys in your .env file. Do not run production instances with default boilerplate values. In particular:
    • RUSTSHARE_SECRET_ENCRYPTION_KEY (AES-256-GCM key used to encrypt secrets at rest).
    • JWT_SECRET (Stateless web session signing key).
  2. Port Isolation: The default production stack overrides bind internal database ports (5432) and backend ports (8080) strictly to 127.0.0.1 to prevent exposing databases directly to the public web.
  3. Log Rotation: Enable standard Docker log rotation rules to avoid filling storage disks with standard request trails: 
    # Inside docker-compose.prod.yml
logging:
  driver: "json-file"
  options:
    max-size: "10m"
    max-file: "5"
  4. Resource Isolation: Impose strict CPU and memory limits on containers to prevent host exhaustions during massive, concurrent uploads.

Reverse Proxy & HTTPS Setup

RustShare does not terminate TLS natively. Production operators must deploy a reverse proxy (e.g., Nginx, Caddy, HAProxy, or Cloudflare Edge Gateways) in front of the stack. Ensure the proxy configures the following headers to support websocket connections and large uploads:

# Recommended Nginx Proxy Configuration
server {
    listen 443 ssl http2;
    server_name rustshare.company.internal;

    client_max_body_size 5G; # Supports large file uploads

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Desktop Client

Deep-dive into the synchronization engine designed for local directory monitoring and file-matching.

Current Status

The desktop client is actively developed as a CLI sync engine paired with a background monitor daemon. It resides in the repository under apps/desktop.

The current implementation focuses on robust, low-level POSIX file operations, ensuring synchronization correctness before wrapping the tool inside a graphical GUI.

What is Shipped Today (v0.3.0)

  • Apple macOS Support: The native compiled macOS binary rustshare-desktop is the primary testbed.
  • Pairing-First Auth: Secure desktop client registration uses a token exchange protocol. Administrators can fall back to explicit --token inputs during debugging.
  • Root Synced Subtrees: Fully mirrors remote nested paths locally, including empty directories and zero-byte placeholders.
  • Full Account Mirror: Supports mapping the root / workspace directly to a local disk path.
  • Quarantine Safeguards: Corrupt server transfers or aborted downloads are automatically quarantined to specific cache routes to avoid blocking the sync queue.
  • Sync Doctor Command: Allows operators to inspect stale or out-of-sync local metadata tables via the CLI: 
    rustshare-desktop sync doctor
  • Remote Cleanup: Stale remote records can be easily pruned using: 
    rustshare-desktop sync cleanup-remote

What is NOT Shipped Yet

The following elements are currently planned but not yet implemented inside the desktop suite:

  • A polished macOS .app bundle container.
  • Notarized drag-and-drop installer packages for macOS and Windows.
  • A finished graphic GUI shell wrapping the sync engine (all status commands currently operate through terminal logs).
Developer Reference

If you want to build the current client from source, consult the markdown instructions located inside the repository: apps/desktop/docs/distribution/macos-client-installation.md.

Operations Guide

A quick-reference dashboard for administrators managing the day-to-day operations of a RustShare node.

Operational Checklist

Starting Services

Ensure your environment variables are configured, then start the stack in detached mode:

docker compose up -d

Stopping Services

Safely stop the running backend and metadata services without destroying volumes:

docker compose down

Checking Service Logs

Monitor startup outputs, JWT validation reports, or database connection pools:

docker logs -f rustshare-backend-1

System Backups

RustShare backups must capture two components to ensure absolute state recovery:

  • Relational Metadata: A snapshot of PostgreSQL state (if using the V1 database profile).
  • Durable Content: Full copies of the underlying S3 storage bucket.

Run the built-in backup script to output an encrypted package: 

./scripts/backup-stack.sh

Restore Validation Drills

Test Your Recovery Path

A backup process is only as good as its tested restore path. We recommend running a recovery drill at least once a quarter using our preconfigured isolated environment.

To run a recovery validation drill locally:

docker compose -f docker-compose.restore-drill.yml up -d
./scripts/final-launch-smoke.sh

Troubleshooting FAQ

Error: Rate limit exceeded on authentication paths.
Solution: By default, authentication paths enforce per-IP limits. If users are behind a corporate NAT, ensure your reverse proxy passes the correct X-Real-IP header, or configure the rate limits in your .env file.

Error: S3 Storage authentication failed.
Solution: Verify that the credentials in .env match the credentials configured in the rustfs administration panel at http://localhost:9001.

Security Model

Understanding the mitigation boundaries, credential policies, and access controls of the platform.

Threat Model Matrix

Threat Target Mitigation Strategy
Unauthorized File Access Secure HttpOnly JWT cookies, token checks on downloads, and explicit ACL evaluation.
Brute Force / Dictionary Attacks Argon2id password hashing and per-IP rate-limiting on login.
Session Hijacking SameSite cookies and CSRF validation on all mutation endpoints.
Data Leak at Rest AES-256-GCM encryption of secrets via RUSTSHARE_SECRET_ENCRYPTION_KEY.
SQL Injections Compile-time query verification in sqlx (preventing raw string generation).

Limitations & Non-Goals

Boundary Limitations Details
Compromised Host OS If an attacker gains root privileges on the server, all encryption keys in memory are exposed.
Unencrypted Transport TLS termination is the responsibility of the operator. Do not deploy without HTTPS.
Malicious Files Automatic virus scanning and executable sandboxing are out of scope for the core platform.
Security Disclaimer

RustShare has not yet undergone an external penetration audit. The current security posture is built on industry standards, type-safe Rust code compilation, strict compiler flags, and automated dependency auditing.

OIDC Integration Status

RustShare supports single sign-on (SSO) authentication using standard OpenID Connect (OIDC) protocols. The system is designed to use the authorization_code flow. While PKCE-based OIDC configuration exists to support mobile and desktop pairing, end-to-end production validation against enterprise identity providers (such as Okta, Azure AD, or Keycloak) is in progress.

Contributing to RustShare

We welcome contributions from developers, technical writers, and security researchers.

Local Development Setup

To compile RustShare and run tests locally, ensure you meet the following requirements:

  • Rust Toolchain: Version 1.95.0 (as specified in rust-toolchain.toml)
  • Node.js: Version 20.0+ (and npm)
  • Docker: Active docker service to run local test databases

Step 1: Start Mock Dependencies

Boot up the developer Postgres database and the MinIO storage server locally:

docker compose -f docker-compose.dev.yml up -d

Step 2: Build the Frontend

Navigate to the frontend folder, install packages, and compile the SPA bundle:

cd frontend
npm install
npm run build
cd ..

Step 3: Build and Test the Backend

Verify that your local environment passes all unit, integration, and formatting tests:

# Run tests
cargo test

# Check formatting
cargo fmt -- --check

# Check for common code anti-patterns
cargo clippy -- -D warnings

Contribution Guidelines

  • DCO (Developer Certificate of Origin): All commits must be signed off (using git commit -s) to certify that you have the right to submit the code under the project's Apache 2.0 license.
  • Code Quality: Write clean, documented, type-safe code. We expect thorough unit testing for all critical API and permission paths.
  • Submitting Pull Requests: Ensure your PR targets the main branch, passes all CI validations, and provides a clear description of the problem solved.

For the complete contribution charter, review the CONTRIBUTING.md file in the repository.

Frequently Asked Questions

Answers to common questions regarding RustShare's design, limits, and deployment path.

General Questions

Is RustShare production ready?

Not yet. RustShare is in a late-MVP / pre-release state. The core web engine and S3-based file sync are highly stable and feature-complete, but OIDC enterprise validation, advanced alerting, and desktop installer suites are still being validated. We recommend testing the platform in staging before deploying it to mission-critical environments.

Is RustShare open source?

Yes. RustShare is licensed under the permissive Apache License, Version 2.0. You are free to download, modify, distribute, and self-host the platform for commercial and private use.

Is it a Dropbox replacement?

No. While it shares basic upload/download capabilities, RustShare is designed as company memory infrastructure. It focuses on structured technical documents, ADRs, project boards, and explicit permission auditability for teams, rather than mass-market consumer camera uploads or generic cloud drives.

Is it a Nextcloud replacement?

Yes, but with a deliberately narrower scope. Nextcloud is a massive suite offering mail, calendars, office suites, and a large app marketplace. RustShare focuses on doing one thing extremely well: high-performance, secure file collaboration for technical teams. We avoid feature bloat to maintain speed, auditability, and ease of deployment.

Does it require a specific cloud provider?

No. RustShare is completely infrastructure-agnostic. You can deploy the Docker containers to AWS, Google Cloud, Azure, on-premise VMs, bare metal servers, or a single Raspberry Pi.

Can I host it in air-gapped environments?

Yes. Because RustShare supports a Zero-PostgreSQL standalone profile and bundles its compiled SvelteKit SPA directly inside the Axum binary, you can host the entire stack locally in isolated, air-gapped corporate subnets with zero external dependencies.

Does it include AI?

AI features (semantic searches, summaries, and indexing) are planned as optional, permission-aware additives. They are not a requirement for the platform's core usability, and they will never execute unauthorized background data leakage.

How does RustShare relate to RustChat?

RustShare is designed to act as the native file and storage layer for the RustChat ecosystem. They share identity models, but they maintain separated databases and strictly bounded API boundaries to prevent security bypasses.
