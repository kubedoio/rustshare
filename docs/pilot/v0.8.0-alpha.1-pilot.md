# Elembra Alpha Pilot — User Guide (v0.8.0-alpha.1)

> **Pilot software.** This is an Alpha: features and data formats may still
> change. It is not production software. Your feedback makes the next version
> better — report problems using the template at the end of this page.

**Versions in this pilot**

| Component | Exact version |
|---|---|
| Elembra server | `ghcr.io/kubedoio/rustshare-backend:0.8.0-alpha.1` |
| Chat relay (Buzz) | `ghcr.io/kubedoio/buzz:sha-8ce4dac` |

---

## 1. Installation and start

Run by the pilot operator (not per-user):

1. Copy `.env.example` to `.env` and fill in the required values
   (`scripts/pre-flight.sh` checks them; it also generates strong secrets).
   Set a strong `RUSTSHARE_ADMIN_PASSWORD` **before** the first start — this
   is the administrator login.
2. Start the stack:
   ```bash
   docker compose -f docker-compose.yml -f docker-compose.alpha.yml -f docker-compose.dogfood.yml up -d
   ```
3. Open `http://<server>/` in your browser.

Chat is turned on by the operator once: **Chat → Enable**. The first enable
connects the server to the Buzz relay automatically (no manual setup).

## 2. Login and onboarding

- The administrator account is created automatically at first start using the
  email/password from `.env`.
- The administrator creates workspaces and user accounts; each user logs in
  with their email and password.
- Two things happen the first time a user opens Chat:
  1. the server pairs their account with their Chat identity (this is the
     **binding** — it decides who can read and write which channel);
  2. their browser creates a personal Chat key.

## 3. Chat key backup and import

Your Chat key proves your identity to the relay. **It lives only in your
browser**, so:

- **Back it up right after your first Chat setup**: open Chat → *Bind
  identity* → **Export key backup**. It copies an encrypted backup to your
  clipboard. Store it somewhere safe, together with the passphrase you chose.
- **Import on another device**: open Chat on the new device → *Compose* →
  **Import key** → paste the backup and enter the passphrase. Without a
  backup, a new device is a new identity (you would appear as a different
  person in channels).

## 4. Files

- Upload a file with **Files → Upload**. Files live in your workspace.
- Share a file with someone by giving them access (share dialog). Access is
  per user: only people you share with can open the file.
- Folders keep things tidy; everything you can see is searchable.

## 5. Chat

- Chat opens a channel list. Messages are delivered live.
- Only members of a channel can see its messages; a channel member who is
  blocked or removed loses access immediately.
- Messages support Markdown and attachments (see below).

## 6. Attachments

- While writing a message, choose **Attach** and pick a file from Files.
- Recipients see an attachment chip on the message. Clicking it opens the
  file **only if you have access to it** (the same access as Files — sharing
  rules apply unchanged). If you don't have access, you get a plain "not
  available" message — nothing about the file is revealed.
- Attachments are references, not copies: update the file in Files and the
  attachment opens the current version.

## 7. Ask

- **Ask** answers questions about what your team wrote, using your own
  messages and files as evidence.
- Ask a question in a workspace, folder, note, or channel scope. The answer
  shows **citations** — click one to open the exact original message or file
  it came from.
- Ask works only if the operator configured an AI provider
  (`ELEMBRA_LLM_API_KEY` etc. in `.env`). If not configured, the Ask button
  simply shows as unavailable.

## 8. Known Alpha limitations

- No reply/thread view yet (planned for a future version).
- Ask needs an operator-configured AI provider.
- Attachments need you to be signed in; there is no preview thumbnail yet.
- Existing deployments that already had a manual Chat setup keep using the
  manual mapping mode — nothing is migrated automatically.
- The upstream security scanner for the Chat relay is still being finalized.

## 9. Reporting a problem

Use this template for every report — it lets us act fast:

```text
Workflow:      (what you were doing — e.g. "Send a file attachment in channel X")
Expected:      (what you expected to happen)
Actual:        (what actually happened)
Severity:      P0 / P1 / P2 / P3   (see below)
Evidence:      (screenshot, log line, timestamp, message id — anything)
Workaround:    (did you find a way around it?)
```

**Severity policy**

| Level | Meaning | What happens |
|---|---|---|
| **P0** | Security breach, data loss, or someone can see/change data they must not | Stops the pilot; engineering responds immediately |
| **P1** | A core workflow is completely blocked | Stops the pilot; engineering responds immediately |
| **P2** | Significant friction (wrong behavior, but a workaround exists) | Fixed in the next release |
| **P3** | Enhancement or polish | Collected for later |

Only P0/P1 stop the pilot. P2/P3 are collected and fixed in the next version.

Send reports to the pilot channel or file an issue in the project repository
using the template above.
