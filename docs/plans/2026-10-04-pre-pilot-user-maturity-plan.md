# RustShare pre-pilot-user maturity plan

**Status:** Proposed execution plan
**Purpose:** Make the bounded FWS/Erasmus pilot dependable for real users before accounts are issued.
**Scope:** Existing RustShare product and authoritative Pilot Release workflow; no Bund expansion.

## Outcome

Before the pilot owner invites the first user, an operator other than the primary developer must be able to deploy a specific revision, configure it without undocumented fixes, verify the supported user journey, handle ordinary account lifecycle events, diagnose failures, and recover the service and its data using the repository runbook.

This is a stricter participant-start gate than the original bounded password-login assessment. The [pilot readiness report](../pilot/pilot-readiness-report.md) now records **NOT READY** under this tightened contract until the account-lifecycle phase passes for an exact candidate. Existing deployment and workflow evidence remains useful baseline evidence; this plan does not replace the authoritative workflow or imply that the broader beta is ready.

## Baseline and scope decisions

- Preserve `.github/workflows/pilot-release.yml` as the authoritative pilot validation workflow. Extend its evidence only when an acceptance item below is not already covered; do not add a parallel all-in-one test harness.
- Carry forward the report's tested deployment and exact revision/evidence references. Re-check the live deployment revision at the start of execution; do not treat an older successful run or a mutable `latest` image as candidate evidence.
- The initial cohort uses the supported password-login path and the existing Notes, Files, sharing, and workspace capabilities exercised by the canonical journey. Do not make OIDC a prerequisite unless the pilot owner changes the cohort requirements.
- Calendar is outside the initial cohort unless a concrete FWS use case is approved. Its HTTPS-only non-loopback policy, provider OAuth setup, encrypted refresh-token handling, sync recovery, and user-consent lifecycle are governed by [ADR-0037](../adr/0037-calendar-application-and-external-sync.md); if Calendar enters scope, add and pass its provider-specific acceptance before user start.
- Chat is outside the initial journey unless specifically approved. If enabled for users, require the authoritative Buzz authorization mode and live conformance checks; do not rely on the coarse local mode. Chat bootstrap failure must remain visible and recoverable. See [ADR-0035](../adr/0035-buzz-source-authorization-gateway.md) and [ADR-0036](../adr/0036-elembra-chat-zero-config-bootstrap.md).
- Treat search as a discovery mechanism, never as permission. Files/Notes results and citations must be reauthorized by their owning source; test the pilot's actual sharing and tenant boundaries. See [ADR-0036: Permission-Aware Unified Search](../adr/0036-unified-search-permission-model.md) and [ADR-0032: ResourceRefs and Authorization](../adr/0032-resource-refs-and-authorization.md).
- Integration events are at-least-once and consumers must be idempotent. If any included pilot operation depends on projections/events, verify delivery, duplicate handling, and visible stuck/dead-letter diagnosis under [ADR-0031](../adr/0031-durable-integration-events.md). Do not make optional event health noise a false application-readiness signal.

## Go/no-go rule

The pilot owner may start the cohort only when every P0 item is evidenced for the same candidate revision and environment, the account recovery/offboarding path is understood, and an operator other than the primary developer has completed the rehearsal. An accepted limitation in the existing readiness report is not automatically accepted for participant start: explicitly review its impact on real users and record the decision, workaround, owner, and expiry/review date.

Do not declare **READY** from a mostly green run. If a mandatory P0 has no evidence, the decision is **NOT READY**. If all mandatory gates pass but a bounded limitation is explicitly accepted and has a safe workaround, report **READY WITH ACCEPTED LIMITATIONS** using the permitted conclusions in the readiness report.

## Evidence and repository touchpoints

- Keep machine-generated run evidence under `docs/pilot/evidence/` or the workflow artifact referenced by the report; include source SHA, build/image identity, deployment/configuration identity, timestamps, phase results, and diagnostics, with secrets and personal data redacted.
- Keep user-facing operating steps in [the pilot runbook](../pilot/runbook.md), acceptance definitions in [the readiness contract](../pilot/pilot-readiness-contract.md), repository findings in [the assessment](../pilot/pilot-maturity-assessment.md), and final disposition in [the readiness report](../pilot/pilot-readiness-report.md). This plan sequences work; it is not a second validation workflow.
- Update the relevant issue/PR and report as evidence is produced. Do not mark an item complete based on documentation edits alone where execution evidence is required.

## ADR implications at a glance

| ADR | Plan implication |
| --- | --- |
| [0037 Calendar and external sync](../adr/0037-calendar-application-and-external-sync.md) | Exclude from the initial journey unless approved; if included, add provider consent/configuration, HTTPS, token, throttling, and resync/recovery gates. |
