# RustShare v0.5.0 Release Plan

## Goal

Cut and publish **RustShare v0.5.0** from the current `main` branch, incorporating all changes since **v0.4.0** (2026-06-04).

## Scope Summary

Key changes since v0.4.0:

- **OpenAPI auto-generation** (`feat: auto-generate OpenAPI spec with utoipa`) — backend now serves a generated `/api-docs/openapi.json` and Swagger UI.
- **Workspace overview dashboard redesign** — refreshed dashboard layout and module rendering.
- **Production-readiness hardening**:
  - Removed hardcoded test DB credentials.
  - Added optional bearer-token auth for the Prometheus `/metrics` endpoint.
  - Exempted `/api/v1/auth/login` from CSRF cookie checks to avoid lockouts with stale session cookies.
  - Documented `SameSite=Lax` rationale for session/CSRF cookies.
  - Paged through unbounded list endpoints in the frontend (decisions, standups, meetings, shares, kanban, brainstorming boards).
- **Repository cleanup** — removed stale root files (`CLAUDE.md`, `convert_files.py`, `quick-fix.sh`, `test-deployment.sh`, `package-lock.json`, public-preview handover directory) and tightened `.gitignore`.
- **Dependency maintenance** — rolled up Dependabot Rust and npm updates, with `aws-smithy-types` and `time` pinned for build compatibility.
- **README polish** — status and positioning refinements.

## Release Steps

The repository uses a tag-driven release workflow (`.github/workflows/release.yml`). The recommended sequence is:

1. **Create a release branch (optional but recommended)**
   ```bash
   git checkout -b release/v0.5.0 main
   ```

2. **Prepare release metadata**
   - Update `CHANGELOG.md` with the v0.5.0 section.
   - If workspace/package versions are pinned to a release version, bump them to `0.5.0`.

3. **Open a release PR**
   - Target `main`.
   - Title: `release: prepare v0.5.0`.
   - Wait for CI to pass.

4. **Merge the release PR**
   - Use a signed-off merge commit (DCO requirement).

5. **Tag the release commit on `main`**
   ```bash
   git checkout main
   git pull origin main
   git tag -a v0.5.0 -m "RustShare v0.5.0"
   git push origin v0.5.0
   ```

6. **Monitor the Release workflow**
   - The `release.yml` workflow will trigger on the tag push.
   - It builds `x86_64` and `aarch64` binaries, builds/pushes a multi-arch Docker image to GHCR, generates SBOMs, attests artifacts, and creates the GitHub Release.
   - Watch for failures in `validate-tag`, `build-binaries`, `build-and-push-image`, `generate-sbom`, `attest-artifacts`, or `create-release`.

7. **Verify the published artifacts**
   - GitHub Release page shows `RustShare v0.5.0` with binaries and SBOMs.
   - GHCR image `ghcr.io/kubedoio/rustshare-backend:0.5.0`, `:0.5`, `:0`, and `:latest` are pushed.
   - Attestations are visible under the release.

## Post-Release

- [ ] Mark the GitHub Release as the latest release.
- [ ] Update deployment manifests (Helm, Docker Compose, etc.) to use `ghcr.io/kubedoio/rustshare-backend:0.5.0`.
- [ ] Run a post-deploy smoke test in the staging/production environment.
- [ ] Announce the release in the project communication channel (Discord/Slack/internal notes) with a link to the changelog.
- [ ] Close the v0.5.0 release plan issue/PR once smoke tests pass.

## Rollback Plan

If a critical issue is discovered after release:

1. Revert the offending commit on `main` (or create a `release/v0.5.1` hotfix branch).
2. Tag and release `v0.5.1` following the same workflow.
3. Update deployment manifests to `0.5.1`.
4. Keep the `v0.5.0` release available for audit/debugging but mark it as deprecated if necessary.
