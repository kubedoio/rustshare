# Phase 4.0 Audit — Files, Notes, Calendar & Resource Sharing Semantics

Baseline: commit `1ec2ea7a887ee0ab79d7d8ce525a0e5a76e0109e` (main, PR #359 merged).
Scope: actual semantics from source and migrations, not intended architecture.
Method: read-only source audit in an isolated worktree; prior-verified facts from the issue #287 evidence matrix treated as given.

## 1. Resource tenant model

**Tenant columns** (migration `backend/migrations/20260329170001_add_tenant_id_to_tables.sql`): `users`, `folders`, `files`, `shares`, `file_versions`, `notifications`, `user_groups`, `file_thumbnails` all got `tenant_id UUID NOT NULL DEFAULT '00000000-0000-0000-0000-000000000000'` — every pre-migration row is nil-tenant, and nil remains a legal tenant value everywhere. `group_members` (`20260322000003_create_user_group_members.sql`) has **no tenant column**. `calendar_sources`/`calendar_events` (`20261001090000_create_calendar_tables.sql:3,38`) carry `tenant_id NOT NULL DEFAULT nil`. `mail_links` (`20260708150001_create_mail_links_table.sql:3`) carries tenant_id but is a message↔target link, not an access grant.

**Share/public-link table shape** — one `shares` table, three row kinds:
- Base: `20260317000005_create_shares_table.sql` (file_id, globally-unique share_token, created_by, permissions, password_hash, expires_at).
- `20260318160000_extend_shares_table.sql`: adds `recipient_user_id`, `folder_id`; exactly one of file_id/folder_id; public rows have token + no recipient.
- `20260401000001_add_group_sharing.sql`: adds `recipient_group_id`; exactly one of token/recipient_user_id/recipient_group_id.
- Capabilities `View|Edit|Admin` (`20260318164708`), plus `upload_only` (`20260320000006`). Partial unique indexes per (resource, group) for active shares (`20260404000003`).
- **Public links = `shares` rows with `share_token`**; user shares = `recipient_user_id`; group shares = `recipient_group_id`. There is no separate public-link table.
- **Note "public share" is not a table at all**: a `NoteVisibility::Public` flag plus an object-storage index `meta/notes/public/{share_id}.json` (`note_service.rs:306-307`, `2729-2765`).

## 2. Share-creation validation — all paths enumerated

| Path | Code | Resource-tenant vs requester | Recipient resolution |
|---|---|---|---|
| Public file link `POST /files/{id}/shares` | `share_service.rs:289-363` | `find_file_by_id(file_id, user_id)` is **owner-scoped only** (`metadata.rs:2775-2785`); ownership required; **no `file.tenant_id == tenant_id` check** | n/a (public) |
| Public folder link `POST /folders/{id}/shares` | `share_service.rs:367-451` | `find_folder_by_id_unchecked` + owner-or-Admin via `check_resource_permission`; **no tenant check** | n/a (public) |
| Group share (file/folder) | `share_service.rs:922-1066` | `resource_tenant != tenant_id → CrossTenantSharingNotAllowed` (**line 954 — the only explicit check**) | **No group existence or group-tenant check at all**; owner/Admin path skips membership check (959-993); `is_user_in_group` has no tenant filter (`metadata.rs:5559-5574`) |
| User share file/folder | `user_share_service.rs:253-372, 380-499` (deprecated service still wired: `user_shares.rs:133-141, 188-201`) | Creator tenant derived (`get_tenant_id_for_user`), resource lookup scoped to it, ownership required | `find_by_email(email, creator_tenant)` — recipient must be in creator's tenant |
| Note publish (not a shares row) | `note_service.rs:2661-2701` | via `file_service.get_file` → only **View** needed | n/a |

So: user-share creation is fully tenant-consistent; group-share creation validates the resource side but never validates the group; public-link creation validates ownership but not resource tenant (matters only for legacy nil-tenant files).

## 3. Share resolution and the C3 asymmetry — VERIFIED PRECISELY

The `PermissionResolver` (`backend/crates/core/src/services/permission_resolver.rs:193-304`) takes a **single `tenant_id`** and uses it for the file lookup, `find_user_share`, `find_group_shares`, and `get_user_group_ids` (the last JOINs `users u … AND u.tenant_id = $2`, `backend/crates/infrastructure/src/repositories/permission_resolver.rs:160-175`). All share-row SQL filters `shares.tenant_id = $tenant` (`share_repository.rs:41-45`; `permission_resolver.rs:79-83,108-112,…`). The tenant filter is only as sound as the tenant the **caller** passes:

- **`FileService::get_file` keys off the FILE's tenant**: `find_file_by_id_unchecked(file_id)` then `require_file_permission(user_id, file.tenant_id, file_id, View)` (`backend/crates/core/src/services/file_service.rs:860-876`, esp. 865, 872). Same pattern in update/delete paths (953, 1143, 1266, 1366, 1457, 1536). The HTTP layer passes only `auth.user_id` and never re-checks tenant: `handlers/files.rs:193-198` (get), 257-264 (download/content). Same for `handlers/notes.rs` entry points that call file-layer ops indirectly.
- **`FilesResourceOwner` (`0032-resource-refs-and-authorization.md` adapter) keys off the REQUESTER's tenant**: `ctx.tenant_id.0` for both existence and permission (`backend/server/src/authz/files_owner.rs:157-167, 237-246, 364`).
- Result: for a synthetic share row `(tenant_id=A, recipient_user_id=<tenant-B user>, file_id=<tenant-A file>)`, `get_file` grants **View** while the source-authorizer returns **Deny/NotFound** — the same database state yields opposite decisions. Exactly the reported C3 asymmetry, confirmed at these line numbers.
- **Reachability: SYNTHETIC only.** No API path can create that row: user-share creation resolves recipients in-creator-tenant; group-share rows point at groups, and group *membership* resolution is tenant-checked (`get_user_group_ids`), so a tenant-B member can never satisfy the filter keyed by tenant A. Consistent-data contract tests cover this (`backend/tests/contracts/tenant_isolation_contract.rs:28, 70, 294`) but do not seed mismatched rows, so C3 is untested at the Files HTTP layer.
- **Notes CLOSE the hole**: every note op post-checks `file.tenant_id != auth.tenant_id → PermissionDenied` (`note_service.rs:1361-1363` get, `1391-1393` reconcile, `2668-2670` toggle_visibility; handlers pass `auth.tenant_id`, `handlers/notes.rs:132, 359, 465`). Notes therefore ride on get_file but cannot expose C3 cross-tenant. **No asymmetry in Notes or Calendar resolution** — notes add the missing check Files lacks.

## 4. Group share resolution

`check_file_permission` step 3 (`permission_resolver.rs:259-281`): `get_user_group_ids(user, tenant)` (tenant = file's tenant on the Files path) then `find_group_shares(file, group_ids, tenant)` which filters `shares.tenant_id = tenant`. So access requires: share row tenant == lookup tenant == **recipient user's tenant** (enforced by the `users.tenant_id` JOIN). In consistent data all coincide. The SHARE's tenant is the operative filter; the group's own `tenant_id` is never consulted at resolution — a nil-tenant or cross-tenant group only shows up as the inventory's `share_group_tenant_mismatches` and stays inert. Inherited folder shares go through the same tenant (`resolve_folder_ancestry`, 433-608). `list_received_shares` is requester-tenant scoped with the same membership subquery (`share_repository.rs:60-94`).

## 5. Calendar

No sharing mechanism exists at all — no share/link/ACL table or endpoint. Every route (`server/src/routes.rs:463-527`) is authenticated and every service call is `(tenant_id = auth.tenant_id, owner_id = auth.user_id)`, enforced in the repository (`calendar_service.rs:649, 727, 985, 1097`; export at `handlers/calendar.rs:324-332` uses the same `get_event`). **Calendar/event links cannot bypass Files/Notes authorization today** — there are no cross-app references from events (the `raw` JSONB is external-provider data) and no shared-calendar reads. Issue #333's calendar concern is about the *proposed* sharing model (ADR-0037), not an existing bypass. Note `calendar_events` owner-scoping also has a deliberate "foreign-tenant delete = successful no-op" behavior (`calendar_service.rs:1086-1136`).

## 6. Public links

- Token lookup is globally unscoped (`get_share_by_token_unscoped`, `metadata.rs:5147-5159`); `resolve_public_share` (`share_service.rs:260-279`) rejects only if a supplied tenant ≠ share.tenant_id. `X-Tenant-ID` is optional; absent/nil ⇒ derive tenant from token (`handlers/public_shares.rs:37-57`); session JWT embeds `tenant_id` (`share_service.rs:508`); session-scoped re-lookups use the tenant-scoped `get_share_by_token` (`metadata.rs:5127-5141`). Matches `0031-tenant-isolation-share-links-and-rls.md` as implemented and tested (`tenant_isolation_contract.rs:70`).
- **Nil-tenant public links work and are self-contained**: all downstream folder/file listing keys off `share.tenant_id`/`target_folder.tenant_id` (`share_service.rs:894-906`), so a nil-tenant share resolves only nil-tenant rows — no cross-tenant exposure, but also no tenant boundary of any kind around it.

## 7. Mismatch inventory (`scripts/pilot-group-scope-inventory.sql` + `backend/tests/pilot_group_scope_inventory_test.rs`)

The script counts, per group: legacy-zero-tenant flags, membership↔group tenant mismatches, share↔group, **share↔resource**, file/folder-owner, and share-creator tenant mismatches, plus expired/revoked/malformed/missing references. The test (`pilot_group_scope_inventory_test.rs:37-300`) seeds exactly the anomaly classes: a nil-tenant group with a tenant-A member (cross-tenant membership), a file in tenant B referenced by a share in tenant C, expired and revoked shares, folder shares — asserting `(true, 1, 1, 1, 1, 4, 2, 1, 1, 3, 1, 4)` mismatch counts — and separately proves the query fails closed (SQLSTATE 42501) under an owner-isolation RLS role (302-362). Mismatches arise from: (a) nil default backfill, (b) `add_group_member` not checking member-vs-group tenant (`admin/groups.rs:440-484` — admin-only, but no tenant check), (c) group-share creation never validating the group's tenant, (d) public-link creation not checking resource tenant.

## Classified findings

1. **C3 decision asymmetry: Files read paths key the permission resolver off the resource's tenant; the ADR-0032 source authorizer keys off the requester's tenant** — `file_service.rs:865,872` vs `authz/files_owner.rs:237-246`. A share row with `tenant_id=A, recipient_user_id=<tenant-B user>` grants View via `GET /api/v1/files/{id}`(+download/content) but Deny via the source-authorization contract. **Classification: correctness defect (inconsistent authorization semantics). Reachability: SYNTHETIC database-state only** (no API can create the row; notes layer closes it at `note_service.rs:1361`). **Implication:** ADR-0032's "owner is final authority" is not yet true — the Files owner adapter and the Files HTTP surface implement different tenant keys. Pick one keying (requester tenant + explicit resource-tenant equality check, as notes do) before extending resource-level permissions.

2. **Notes close C3 with a post-hoc tenant equality check that Files lacks** — `note_service.rs:1361-1363` etc. **Classification: intended and tested behavior for Notes; by contrast it is a defense-in-depth weakness in Files** (every Files handler omits the equivalent check; `handlers/files.rs:193-198,257-264`). **Reachability: DIRECT API surface affected, synthetic-state only.** **Implication:** the nil-tenant compatibility and cross-tenant restriction decisions should standardize on the notes pattern (`resource.tenant_id == principal.tenant_id`) as an invariant at the service boundary.

3. **View-level share recipient can publicly publish a shared note** — `toggle_visibility` only calls `get_file` (View) and then flips `visibility=Public` + writes a public index (`note_service.rs:2667-2701`); `get_public_note` serves it unauthenticated (2729-2765). **Classification: confirmed access bypass (privilege escalation View → public disclosure). Reachability: DIRECT API today** (no tenant inconsistency needed; within-tenant escalation). **Implication:** resource-level permission model must distinguish "read" from "publish"; publishing should require Edit/Admin or ownership.

4. **Group-share creation performs no group existence/tenant validation on the owner/Admin path** — `share_service.rs:922-1066` never loads the group; `GroupNotFound` is mapped in the handler but never returned; membership check skipped for owners (959-993). **Classification: correctness defect. Reachability: DIRECT API** (share rows pointing at arbitrary/nonexistent/cross-tenant group UUIDs can be created), **but inert in consistent data** because resolution tenant-checks membership via `users.tenant_id`. **Implication:** share tenant model must validate recipient-tenant == resource-tenant at creation; the ADR-0031-style "validate at creation" principle is incompletely applied.

5. **Public-link creation does not verify `resource.tenant_id == requester tenant`** — `share_service.rs:289-363, 367-451` check ownership only. For legacy nil-tenant files this creates share rows whose tenant ≠ file tenant (an inventory `share_resource_tenant_mismatch`), and such links resolve oddly (token route unscoped; resource lookups keyed by mismatched tenants). **Classification: legacy compatibility concern + correctness defect. Reachability: DIRECT API, only for nil-tenant (legacy) resources.** **Implication:** nil-tenant compatibility needs an explicit policy (backfill vs. reject vs. treat-nil-as-requester) rather than accidental per-endpoint behavior.

6. **New groups are still created with nil tenant** — `admin/groups.rs:181-192` and SCIM v2 `scim_v2.rs:492-506` INSERT without `tenant_id`, taking the nil default; SCIM's `default_tenant_id` is used for users, not groups. **Classification: correctness defect / perpetuated legacy condition. Reachability: DIRECT API.** The nil-tenant population the #287 evidence treats as "legacy" is growing, keeping the nil-tenant collapse class (nil user + nil group + nil share + nil file all mutually reachable) alive rather than shrinking. **Implication:** nil-tenant compatibility decision is blocking — any institutional authz model must first stop producing nil-tenant rows.

7. **Admin `add_group_member` does not check member tenant vs group tenant** — `admin/groups.rs:440-484`. **Classification: correctness/defense-in-depth weakness. Reachability: DIRECT API (admin-only).** Produces `membership_group_tenant_mismatches`; still inert for file access because `get_user_group_ids` filters by user tenant, but it invalidates the assumption that group membership implies same-tenant — an input to any group-scope authorization design.

8. **Parallel unscoped permission evaluator** — `check_resource_permission` (`share_service.rs:1240-1345`) uses `get_file_shares`/`get_folder_shares`/`is_user_in_group`, none tenant-scoped (`metadata.rs:5194-5225, 5559-5574`). It gates share management (folder public links, group shares, revoke/update). **Classification: defense-in-depth weakness. Reachability: synthetic-state sensitive** (mismatched share rows could satisfy Admin checks); consistent data unaffected. **Implication:** two evaluators with different scoping rules (resolver = tenant-scoped; this one = unscoped) must be unified before resource-level permissions are declared authoritative.

9. **RLS is owner-isolation, not tenant isolation, and is not set on the app connection path** — policies `owner_id = current_setting('app.current_user_id')` on files/folders/file_versions only (`20260507000001_add_row_level_security.sql`); shares table explicitly excluded; the no-op middleware was removed per ADR-0031. **Classification: intended and tested behavior (with decorative-RLS caveat confirmed).** Repository-level tenant filtering is the only live tenant boundary, which makes findings 1-8 (application-layer checks) the entire control surface.

10. **Calendar has no sharing and cannot bypass Files/Notes authorization** — owner+tenant scoped throughout (`calendar_service.rs`, `handlers/calendar.rs:291-332`). **Classification: intended and tested behavior (24 ignored PG integration tests per the #333 plan).** The #333 calendar concern is prospective (ADR-0037), not an existing defect.

**Cross-cutting:** every exploitable class above requires either inconsistent/mismatched rows (synthetic) or nil-tenant data (legacy-live); in fully consistent, non-nil data the tenant boundary holds at the API today, and the tenant-isolation contract tests (`tenant_isolation_contract.rs`) plus the inventory test document that. The gate-relevant gaps for the ADR decisions are: (i) unify the resolver tenant keying (finding 1) before resource-level permissions; (ii) validate recipient/group/resource tenant equality at every share-creation path (4, 5); (iii) decide nil-tenant policy and stop producing nil-tenant groups (5, 6); (iv) treat publish as a distinct capability (3); (v) collapse the dual evaluators (8).

## Post-execution corrections (Phase 3 evidence)

The executed negative-test run (`docs/audits/2026-10-13-phase4-0-tenant-isolation-negative-tests.md`, cases a-j; evidence matrix rows `P4-*`) confirms findings 1, 3, 4, 5, 6, 7, 9 and 10 above, and refines two of them:

- **The nil-tenant "collapse" direction in finding 6 must be stated more precisely.** The prior #287 claim that a nil-tenant user in a nil-tenant group reaches a *tenant-A* file through a nil-tenant share row is refuted: on the Files path the resolver's lookup tenant is the *file's* tenant and `get_user_group_ids` requires `users.tenant_id = <lookup tenant>`, which a nil-tenant user fails. What was executed as real is (i) mutual reachability *within* the nil/default tenant — which in a default deployment is produced by ordinary API calls, and (ii) the reverse direction: a **real-tenant** principal reaching a **nil-tenant** resource through a nil-tenant share row (same class as finding 1/C3). The severity is unchanged; the dangerous direction is the reverse of the one originally described. Finding 6's core point — that admin/SCIM paths keep manufacturing nil-tenant groups — stands and is executed (case b).
- **C3 (finding 1) is now executed, not merely inferred**: identical rows yield `DirectShare:View` under file-tenant keying and `NULL` under requester-tenant keying (case f). Reachability remains SYNTHETIC, and share creation still validates resource tenant == requester tenant (`share_service.rs:953-956`).
- **Newly executed**: group-share creation accepts an owner who is not a member of the recipient group (live `201`), consistent with the skipped `is_member` check at `share_service.rs:959-993`.
