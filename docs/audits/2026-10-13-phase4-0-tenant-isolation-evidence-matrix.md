**Ground truth taken from the orchestrator and re-confirmed at source** (all four checked by reading the cited lines): `scim_v2.rs:140-142/205-215` unscoped user reads; `note_service.rs:897-909/943` group-tenant-filtered index refresh; `admin/groups.rs:181-187` tenant-less group INSERT; `bootstrap.rs:124-138` nil pool context. These are the orchestrator-verified rows `P4-01`, `P4-02`, `P4-08`, `P4-31`, `P4-38`.

**Correction produced by this audit (executed).** The Phase 4.0 tenant-identity audit's finding **F4** ("SCIM disable does not revoke credentials; re-enable resurrects device tokens") is **not supported at the baseline commit**: migration `20261003090000_revoke_credentials_on_user_disable.sql` (tracked at `1ec2ea7a`) installs an `AFTER UPDATE OF disabled_at` trigger that deletes `user_sessions` and revokes `device_tokens` for *every* writer, SCIM included. Executed end-to-end reproduction in the disposable database: after the exact SCIM `UPDATE users SET disabled_at = NOW() …`, web sessions = 0 and live device tokens = 0; a subsequent re-enable does not resurrect tokens. See row `P4-10`. The handler-level observation (SCIM code itself performs no explicit revocation, unlike `admin/users.rs:626-649`) is accurate; the *effect* claim is refuted. **This mattered beyond the audits: `docs/adr/0040-organization-tenant-and-workspace-identity.md` decision D8 had reproduced "F4" as its rationale** ("so a re-enabled user's old device tokens work again (F4)"). D8's direction (one disable implementation for all entry points) was harmless, but its stated premise was false at this baseline. **The correction has since been applied:** ADR-0040 D8 is re-anchored on the `users_disable_revokes_credentials` trigger, with the residual stateless-JWT gap recorded as its own approval item, and §7.2 below marks the item Applied. This audit wrote no ADR text itself.

## 2. Decisive environment facts

These facts govern the interpretation of every other row: they determine whether RLS is an enforcement layer at all.

| ID | Fact | Evidence class | Observed |
|---|---|---|---|
| E1 | The shipped application role is a bootstrap superuser **and** the owner of every RLS table **and** `BYPASSRLS`. | `SQL on disposable DB — executed here` (`docker-compose.yml:7-13` runs `pgvector/pgvector` with `POSTGRES_USER: rustshare`; no initdb script exists for any compose file) | `rustshare \| is_superuser=t \| bypassrls=t \| createdb=t \| createrole=t`; all 6 RLS tables owned by `rustshare` |
| E2 | `relforcerowsecurity = false` on every RLS table; `FORCE ROW LEVEL SECURITY` appears nowhere in the repository. | `SQL on disposable DB — executed here` + repo-wide grep | 6/6 tables `force_rls=f`; grep for `FORCE ROW LEVEL SECURITY\|relforcerowsecurity` over `backend/migrations`, `backend/server/src` returns no matches |

| E9 | Database-level guards are limited to credential/chat revocation triggers and blob-GC queueing: **nothing in the schema enforces tenant matching** on groups, membership, or shares. | `SQL on disposable DB — executed here` (full `pg_trigger` inventory) | 20 triggers: 14 × blob-GC queue/cancel, 2 × chat revocation, 2 × credential revocation, 1 × GC serialisation, 1 × `users` delete cascade helper. **Consequence.** RLS in the shipped configuration is decorative: the role bypasses it, `FORCE` is off, and even if enforcement were reached the nil branch passes all rows and the policies carry no tenant predicate. The effective tenant boundary is the application-level `owner_id` / `tenant_id` predicates in the repositories and services.

## 4. Does the tenant boundary hold?

**In consistent, non-nil data the boundary holds at the API — via application predicates, not RLS.** Repository/service tenant filters (`owner_id` + `tenant_id`, share-row tenant filters, the `users.tenant_id` join in `get_user_group_ids`) are the entire control surface (E1–E5). Where those predicates are consistently applied, the executed probes and the prior matrix agree: a same-tenant group member resolves the group, the share and the resource (`P4-30`, `#287-R13`), a cross-tenant requester and a non-member admin resolve nothing (`#287-R14`, `P4-30`), and search reauthorizes every candidate live (`P4-32`).

**Surfaces that are installation-global by construction** — these are not tenant boundaries and must be scoped or explicitly exempted before ADR-0038 decision 1 can be claimed as satisfied:

- **SCIM v1 and v2** (`P4-01`…`P4-05`): one environment-wide bearer token, tenant-blind list/read/update/delete, and v1 provisioning into a client-supplied tenant. This is the only *content-plane-external* surface with a demonstrated cross-tenant read (executed: rows from two tenants returned by the verbatim `WHERE 1=1` query).
- **Admin users and groups** (`P4-06`…`P4-09`, `P4-15`, `P4-18`): all `/api/v1/admin/*` handlers take the global `AdminUser` and none scope by tenant; admin creation paths also manufacture nil-tenant rows, growing the ambiguity the ADR refuses to resolve by inference.
- **Group membership and rosters** (`P4-09`, `P4-15`, `P4-16`): membership is not tenant-bound, and group rosters leak usernames/emails across tenants to any member; the group's own `tenant_id` is never consulted.

**Synthetic-only findings, and why** — the following are real defects but currently unreachable from the API:

- **`P4-22` (C3 tenant-key asymmetry, Files)**: reachable only with a share row whose tenant differs from the recipient's tenant. No API path can create it — user-share creation resolves recipients inside the creator's tenant, group-share resolution is tenant-checked through the `users.tenant_id` join, and group membership resolution is filtered (executed probe: cross-tenant requester resolves 0 groups). The executed SQL shows the divergent decisions exist the moment such a row exists.
- **`P4-25`, `P4-28`, `P4-16`, `P4-36`**: share-management and group-tenant gaps are inert only because resolution filters on the *share's* tenant. Removing or weakening any one of those filters converts them into content bypasses.
- **`P4-43`, `P4-44`, `P4-46`**: only reachable if RLS stops being bypassed (hardened role + nil fallback removed). They are the reason hardening must be staged; `P4-44` then becomes destructive rather than merely wrong.

**Still produced today, not legacy-only** — nil-tenant rows are manufactured continuously: `RUSTSHARE_DEFAULT_TENANT_ID` is unset and defaults to nil (E6), admin/SCIM group creation omits `tenant_id` (executed: `P4-08`), admin user creation omits it (`P4-07`), and the nil UUID is simultaneously the RLS permissive sentinel (E3/E4). The nil-tenant population treated as "legacy" in #287 is therefore growing (`#287-R16`/`R17`, `P4-14`).

**One audit finding is withdrawn by executed evidence:** tenant-identity **F4** (SCIM disable does not revoke credentials; re-enable resurrects device tokens) is refuted — see `P4-10`, and the correction recorded for `docs/adr/0040` D8 in §7.2 (Applied). Any document citing F4 must cite `P4-10` instead.
