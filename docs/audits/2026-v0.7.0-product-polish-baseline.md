## Issue #181 — Block remote images by default in message preview

**Layer:** cross-layer (backend sanitization + frontend rendering).

### Current behavior

- Remote (IMAP) message bodies are fetched via
  `GET /api/v1/mail/accounts/{id}/messages/{uid}/body`
  (`backend/server/src/handlers/mail.rs:1447`) and returned as **raw, unsanitized** HTML
  (documented at `mail.rs:1393`).
- The frontend sanitizes with isomorphic-dompurify in
  `frontend/src/lib/editor/adapter/security.ts:72-86` and then **unconditionally strips
  every remote `<img src>`** (`http://`, `https://`, `//`) at `security.ts:77-85`.
- Imported (stored) message HTML parts are additionally sanitized server-side with ammonia
  in `sanitize_email_html` (`backend/server/src/handlers/mail.rs:1940`), applied at
  render time in `get_mail_message_part` (`mail.rs:2040`), with a
  `Content-Security-Policy: sandbox` header (`mail.rs:2050`). `img src` values with
  `http:`/`https:`/`//` are removed by the attribute filter.
- **Remote images therefore never load today** (good), but they disappear **silently**:
  no placeholder, no privacy notice, and no per-message "Load remote images" action
  exists anywhere.
- `cid:` images: backend rewrites `cid:<content-id>` → `/api/v1/files/{file_id}/preview`
  via `rewrite_cid_urls` (`mail.rs:1963`) **only for imported messages**. The frontend
  never resolves `cid:` URLs, so inline images render broken in the remote preview pane.
- List view renders no HTML (text only), so it cannot leak.
- The preview pane (`MailModuleView.svelte:914`) and the saved-message detail page
  (`routes/(app)/modules/mail/messages/[messageId]/+page.svelte:391`) are **two divergent
  renderers**; both use `{@html}` after sanitization.

### Reproduction steps

1. Configure an IMAP account; open an HTML message containing
   `<img src="https://tracker.example/pixel.gif">`.
2. Observe: no network request is made (correct), but the user is shown nothing about
   blocked images and has no way to load them.
3. Open an HTML message with an embedded `cid:` image in the remote preview: broken image.

### Existing API contract

- Remote body: `MailRemoteMessageBodyResponse{ ..., text, html (RAW), attachments[] }` (`mail.rs:1381`).
- Imported part: raw byte response (sanitized HTML), `Content-Security-Policy: sandbox`.

### Existing tests

- `security.test.ts:19-38` (remote-image stripping), `mail.rs:3114/3124`
  (`sanitize_email_html_strips_scripts`, `sanitize_email_html_blocks_remote_images`),
  `MailModuleView.test.ts:156-163` (sanitize-on-render).

### Security/privacy impact

Privacy boundary. Current default (strip) is safe; the change must keep sanitization
independently effective and make remote loading strictly opt-in per message.

### Minimum safe fix

- Sanitizer gains a "block with placeholder" mode instead of silent stripping: replace
  remote `src` with a `data-blocked-src` attribute and render a placeholder, so an
  explicit per-message action can restore originals client-side without re-fetch.
- "Load remote images" per-message action in both renderers; affects only the current
  message; switching messages resets to blocked.
- Resolve `cid:` images in the remote preview (map `content_id` → attachment bytes
  endpoint) or document the limitation if the MIME part is absent.
- Regression tests: external `img`, `srcset`, tracking pixel, `cid:` present/missing,
  malformed HTML, script injection, plain text, explicit load, message switch.

### Non-goals

Global sender allowlists, trust learning, tracking-pixel classification, backend HTML
rewrite of remote bodies (keep client-side rendering contract).

## Issue #182 — Deterministic ascending/descending date sorting

**Layer:** cross-layer (API contract + storage query + frontend control).

### Current behavior

- Imported list: `list_mail_messages_page`
  (`backend/crates/storage/src/metadata.rs:806-844`) hard-codes
  `ORDER BY imported_at DESC, id DESC` with keyset pagination on `(imported_at, id)`.
  It orders by **import time, not the message date** (`sent_at`), and has **no sort
  parameter**.
- Remote list: `fetch_message_summaries` (`backend/server/src/services/imap_client.rs:348`)
  sorts UIDs descending in memory (UID as date proxy) and paginates with a `before_uid`
  cursor. No date sorting, no sort parameter.
- Frontend: no sort control; messages rendered in server order
  (`MailModuleView.svelte:133`); no pagination UI (hard-coded limit 100 remote / 50 saved).
- Schema: `mail_messages.sent_at TIMESTAMPTZ` (Date header) and
  `imported_at TIMESTAMPTZ NOT NULL DEFAULT now()`; index
  `idx_mail_messages_sent_at ON (tenant_id, sent_at DESC)` already exists
  (`backend/migrations/20260707150001_create_mail_tables.sql:34`).

### Reproduction steps

1. Import messages whose Date header differs from import order (e.g. an old archive).
2. Open "Saved to RustShare": ordering follows import time, not message date; there is no
   control to change direction.

### Existing API contract

- `GET /api/v1/mail/messages?limit&search&cursor_at&cursor_id` →
  `{ messages, next_cursor_at, next_cursor_id }`.
- `GET /api/v1/mail/accounts/{id}/messages?folder&limit&cursor&search` →
  `{ messages, next_cursor }`.

### Existing tests

- No ordering tests for the page query; no API-contract test for sort values.

### Compatibility/security impact

Compatibility-sensitive: callers omitting sort must keep newest-first. Newest-first must
now mean **`sent_at` (message date) newest first** — this is a deliberate, documented
behavior change from `imported_at` ordering; `sent_at` falls back to `imported_at` when
NULL.

### Minimum safe fix

- Typed sort enum (`date_desc` default, `date_asc`) on the imported-list endpoint;
  SQL `ORDER BY COALESCE(sent_at, imported_at) <dir>, id <dir>` applied before keyset
  limit; keyset predicate extended to the new key. Invalid values → 400 validation error.
- Remote list: sort fetched header summaries by parsed Date (+ UID tiebreak) in the
  handler before cursor slicing; document UID-cursor interplay.
- Frontend: sort control, default newest first, persisted across refresh and navigation
  (query cache key + local state seed), never client-side array reversal.
- Tests: both directions, equal dates, multiple pages, search + sort, invalid value,
  empty mailbox.

### Non-goals

Sorting by subject/sender/size; server-side IMAP SORT extension negotiation; full
pagination UI (tracked separately if at all).

## Issue #183 — Attachment filenames, metadata, and downloads

**Layer:** cross-layer, mostly backend + frontend display.

### Current behavior

- Attachments are parsed by mailparse in
  `backend/crates/core/src/services/eml_parser.rs` (`process_leaf_part`, line 172);
  mailparse performs RFC 2047/2231 decoding internally; fallback name `attachment-{idx}`.
- Metadata stored in `mail_attachments` (filename, mime_type, size_bytes,
  content_disposition, content_id, blob_key, file_id) — migration
  `20260707150001_create_mail_tables.sql:54-66` + `20260716000000`.
- **Imported** attachments have stable UUID ids but **no dedicated download endpoint**;
  the detail page offers "Open file" via the linked `files` row when `file_id` exists
  (`[messageId]/+page.svelte:406-437`), otherwise only a `mail-only` badge with no
  download.
- **Remote** attachments download by **positional index**
  (`GET .../messages/{uid}/attachments/{index}`, `mail.rs:1527`), re-fetching and
  re-parsing the entire RFC822 source per download; bytes are the decoded MIME part.
- Filename safety: `safe_attachment_artifact_filename` exists for stored artifacts
  (mail_service tests ~4560); the remote download response headers need review for
  Content-Disposition correctness with hostile names.
- Raw EML download exists only on the saved detail page (`Download .eml` →
  `/mail/messages/{id}/source`); absent from the three-pane viewer.
- Inline parts: tracked via `content_disposition`/`content_id`; parser keeps body parts
  that also carry a Content-ID out of the attachment list (eml_parser `body_slot_open`).

### Reproduction steps

1. Remote message with two attachments: each downloads correct bytes but the whole EML is
   re-fetched per download; check the `Content-Disposition` filename for a Unicode or
   `..`-containing name.
2. Imported message whose attachment has no `file_id`: no download is possible at all.

### Existing API contract

- `GET /api/v1/mail/messages/{id}/attachments` → metadata list.
- `GET /api/v1/mail/accounts/{id}/messages/{uid}/attachments/{index}?folder=` → bytes.
- `GET /api/v1/mail/messages/{id}/source` → raw EML (`message/rfc822`).

### Existing tests

- `eml_parser_test.rs` (5 tests incl. unnamed inline part, body+Content-ID part);
  filename sanitization unit tests in mail_service; no header-injection negative tests.

### Security impact

Filename → `Content-Disposition` is header-injection and path-trust sensitive. Human
security review required.

### Minimum safe fix

- Strict response-filename sanitizer (ASCII fallback + RFC 5987 `filename*=` for Unicode;
  strip control chars, quotes, separators, path traversal) applied on every
  attachment/source download.
- Imported attachments: add `GET /api/v1/mail/messages/{id}/attachments/{attachment_id}`
  serving exact stored bytes (blob_key/file_id), so downloads do not depend on the Files
  module link; keep "Open file" as-is.
- Frontend: raw `.eml` download action in the three-pane viewer; distinct labels for
  attachment vs raw message; unique fallback names in UI (`Attachment 1`, `Attachment 2`).
- Negative tests: `../`, quotes, CRLF, control chars, empty/missing/duplicate/very long
  names; zero-byte; missing blob → 404/410; cross-tenant → 404.

### Non-goals

Attaching Files objects to outgoing mail, per-type preview, Files conversion.

## Issue #184 — Reliable move and archive actions

**Layer:** cross-layer, mostly frontend completeness + IMAP connector robustness.

### Current behavior

- Backend: `POST .../messages/{uid}/move|archive|trash` exist
  (`mail.rs:1586/1618/1659`). `move_imap_message` (mail_service.rs:1431) requires server
  `MOVE` capability; servers without it get a hard error — **no COPY+delete fallback**
  (mail_service.rs:3871). UIDVALIDITY is checked (409 on mismatch).
- Frontend: Move exists for single message (`MailMoveModal`) and in the bulk bar
  (`MailModuleView.svelte:946-989`); **`archiveMessage`/`trashMessage` API functions
  exist but are wired to no UI**. Delete is a hard `DELETE`.
- Archive destination is resolved server-side from the IMAP `\Archive` special-use flag
  (`folder_role`, imap_client.rs:675); folders are live-fetched, never persisted.
- Bulk actions use `Promise.all` per UID (`runForSelection`, `:401-415`) then refetch —
  no partial-failure reporting, no in-progress duplicate guard beyond button state.
- All list state (folder, selection, search) is component-local and **lost on any
  navigation** (detail is a separate route).

### Reproduction steps

1. Select a message in Inbox: toolbar shows Move but no Archive button.
2. Against a server without MOVE capability: move fails with a hard error.
3. Bulk-move 3 messages where the 2nd fails remotely: no per-item error is surfaced.

### Existing API contract

- `MailMessageMoveRequest{folder, destination_folder, source_uidvalidity}`;
  `MailMessageActionRequest{folder, destination_folder, source_uidvalidity}` for
  archive/trash (`require_destination_folder`, mail.rs:175).

### Existing tests

- Service unit tests with `ImapMailboxSession` mocks (move, uidvalidity); no
  COPY-fallback tests; frontend tests cover move modal invocation only.

### Compatibility impact

None on data; IMAP semantics must remain authoritative after refresh.

### Minimum safe fix

- Wire Archive (and Trash where appropriate) into the viewer toolbar and bulk bar using
  the existing endpoints; resolve Archive folder via folder role, error clearly when no
  archive folder exists.
- COPY+`STORE \Deleted`+EXPUNGE fallback when MOVE is unsupported (guarded by UIDPLUS
  capability check), keeping the hard error only when neither is possible.
- In-progress guards against duplicate submission; per-item failure reporting for bulk
  ops with list rollback/refetch; keep counts consistent via refetch.
- Tests: single/batch move, archive, same-mailbox guard, missing destination, remote
  failure, partial failure, repeated click, keyboard/screen-reader access.

### Non-goals

Drag-and-drop, undo, custom shortcuts, cross-module compose.

## Issue #185 — Vault WebUI Markdown editing reliability/conflict safety

**Layer:** cross-layer; backend save contract already strong, frontend gaps.

### Current behavior

- Save is already compare-and-swap: `save_file_content_for_webui`
  (`backend/crates/core/src/services/vault_sync_service.rs:500-634`) — blob put under
  per-key advisory lock, then one transaction bumping `vaults.server_rev` and updating
  `vault_files ... WHERE server_rev = $expected` with `RETURNING`; conflict → structured
  409 `{error:"conflict", client_rev, current_rev, server_sha256}`
  (`backend/server/src/handlers/mod.rs:328-342`). Success is returned only after blob +
  DB commit. Orphaned blobs go to the GC queue. Policy is enforced twice (service + SQL).
- Sync propagation: manifest polling; `last_writer_device_id = web_ui` synthetic device;
  no events/audit entries for WebUI edits.
- Frontend editor (`frontend/src/lib/components/vaults/VaultFileEditor.svelte`) is a
  `<textarea>` with dirty tracking, save states, Ctrl+S, 409 handling and a reload banner.
- **Gaps:**
  1. `ApiError` discards the structured 409 body (`frontend/src/lib/api/client.ts:106-114`),
     so `err.current_rev` is always `undefined`; stale detection depends on refetch racing.
  2. **No unsaved-changes navigation guard** (no `beforeunload`/route-leave prompt).
  3. Conflict UX is reload-and-lose: no copy/download of local unsaved content.
  4. `hasConflict` fires on any rev mismatch even when remote content is identical.
  5. No HTTP-level tests for the `/content/*` endpoints; no test that a WebUI save is
     observed by the next manifest poll.

### Reproduction steps

1. Edit a vault note in the WebUI, then navigate away: no warning; edits lost.
2. Edit in WebUI while an Obsidian client syncs a newer revision, then save: 409 appears,
   but the only offered path is Reload (local text lost unless manually copied).

### Existing API contract

- `PUT /api/vault-sync/v1/vaults/{vault_id}/content/{*path}` body
  `{content, expected_revision}` → 200 `{...new revision...}` | 409 structured conflict |
  403 policy/not-editable | 401 unauthorized.

### Existing tests

- Service unit tests (vault_sync_service.rs:3072-3630): success/conflict/tombstone/policy/
  size/auth. Frontend: `VaultFileEditor.test.ts` (save, 409, 403, races). No HTTP
  `/content/*` tests.

### Data-safety impact

Synchronized user content; conflict handling. Human data-safety review required.

### Minimum safe fix

- Propagate structured 409 fields through `ApiError` (`current_rev`, `server_sha256`).
- Conflict UX: keep local text, offer "Copy my changes" and "Download my version",
  offer "Reload server version"; never silently overwrite.
- `beforeunload` + in-app route-leave guard when dirty.
- Suppress conflict badge when remote sha256 equals local saved content.
- Backend HTTP tests for `/content/*` (success, stale rev 409, policy 403, unauthorized,
  revoked device on sync path); test WebUI write visible via next manifest.

### Non-goals

Real-time collaboration, three-way merge, diff view, binary editing.

## Issue #154 — Clean first deployment / automatic bucket bootstrap

**Layer:** backend startup + deployment artifacts + docs.

### Current behavior

- Bucket bootstrap exists: `ensure_bucket_exists`
  (`backend/crates/storage/src/object_store.rs:456-510`) — `head_bucket`, create on
  failure, idempotent handling of `BucketAlreadyOwnedByYou`/`BucketAlreadyExists`.
  Enabled by default in compose (`RUSTSHARE_OBJECT_STORE_AUTO_CREATE_BUCKET=true`,
  `docker-compose.yml:64`); serde default is `false` (`config.rs:96-98`).
- Readiness includes `head_bucket` (`handlers/health.rs:97-104`) — unreachable/forbidden
  storage fails readiness correctly.
- Startup failure (bad credentials/unreachable) aborts the server; no compose
  `restart:` policy and **no backend healthcheck**, so recovery depends on manual restart.
- `head_bucket` error conflates "missing" with "unreachable/forbidden": with
  `auto_create=true`, a 403 from bad credentials falls into the create path and produces
  a confusing error.
- No dedicated unit test for `ensure_bucket_exists`; integration coverage is incidental
  (stores built with `auto_create_bucket: true` in ignored tests).
- rustfs compose healthcheck is TCP-only (`nc -z`), not S3-API-level.

### Gaps to validate/fix

- Add targeted tests for bootstrap paths (already-exists variants, create, forbidden,
  unreachable) where feasible without live S3, plus a smoke assertion in scripts.
- Distinguish NotFound from other head errors before attempting create.
- Consider compose `restart: unless-stopped` + backend healthcheck on `/health/ready`.
- Clean-VM evidence still required by the issue before closure.

## Issue #132 — Quickstart on clean Linux

**Layer:** docs + deployment artifacts.

### Current behavior / findings

- README quickstart (`README.md:74-89`) marks `scripts/pre-flight.sh` as **optional**,
  but `.env.example` ships empty secrets (`JWT_SECRET`, `POSTGRES_PASSWORD`,
  `RUSTFS_ROOT_PASSWORD`, ...). A verbatim quickstart fails backend config validation
  (`bootstrap.rs:528-538`). **Quickstart defect.**
- `RUSTSHARE_ADMIN_PASSWORD` is empty in `.env.example` and passed through compose as
  **set-but-empty** (`docker-compose.yml:82`); `bootstrap.rs:657` then hashes an empty
  password and skips the random-bootstrap-password file. Same pattern for the demo
  viewer (`auth.rs:331-350` only skips when vars are *unset*). Must be verified at
  runtime; if confirmed it is a first-boot login defect.
- `STORAGE_*` vs `RUSTFS_*` variable duplication in `.env.example` is confusing;
  pre-flight only presence-checks `STORAGE_*` while the backend reads `RUSTFS_*`.
- `final-launch-smoke.sh` does not call `/health` or `/health/ready` and does not test
  share revocation.
- Migrations run automatically at server start (`bootstrap.rs:129`).

### Minimum safe fix

- Make the documented quickstart self-consistent: either pre-flight is a required step in
  README/DEPLOYMENT, or `.env.example` ships generated-on-copy instructions that work.
- Treat empty `RUSTSHARE_ADMIN_PASSWORD`/viewer password as unset in bootstrap/seed
  logic (smallest safe change) or make compose omit them when empty.
- Extend smoke script with `/health` + `/health/ready` and share revoke coverage.
- Then run the clean-environment matrix (Ubuntu 22.04/24.04, Debian 12) and post evidence.

### Non-goals

Changing the supported-platform matrix without documented approval.
