# ADR-0001: Adopt a Hybrid, Object-Store-Centered, Service-Oriented Architecture for RustShare

**Status:** Accepted  
**Date:** 2026-03-30  
**Owners:** RustShare founders / architecture / platform engineering  
**Related:** superseded early planning documents (removed; see repository history).

---

## Context

RustShare is being built as a modern file-sharing platform in the category of Nextcloud, Seafile, OpenCloud, and Dropbox-style systems, with a strategic requirement to integrate cleanly with RustChat.

The product direction is no longer a generic file-sync tool. RustShare is intended to serve security-conscious technical organizations that need:

- self-hosted or private-cloud deployment options
- controlled internal and external sharing
- strong auditability and clear permissions
- lightweight clients
- a native-feeling bridge between files and team communication
- future AI capabilities on top of authorized content

The MVP already exists and partially implements important flows. The question is not whether RustShare can be rewritten into a theoretically elegant platform, but what architecture should be chosen now so the product remains practical, secure, and extensible.

Several architectural directions were considered:

1. PostgreSQL as the single backend for blobs, metadata, permissions, and events
2. Distributed or POSIX filesystem as the main substrate
3. Object storage only, with metadata derived from object state
4. Hybrid architecture: object storage for blobs and versions, explicit metadata/permission authority, asynchronous projections for search/AI/previews/notifications

The design work concluded that a realistic 2026 file platform should not collapse all concerns into one storage primitive.

---

## Decision

RustShare will adopt a **hybrid, object-store-centered, service-oriented architecture**.

### Core decision

RustShare will use:

- **S3-compatible object storage** as the durable blob and version substrate
- an **explicit metadata + permission authority** as the namespace truth
- **event-driven projections** for search, previews, AI indexing, notifications, and secondary read models
- **shared identity but bounded service integration** with RustChat
- **Rust** as the core backend implementation language for security-sensitive services

### Architectural boundaries

RustShare will be organized around these functional layers:

1. **Identity and tenant layer**  
   OIDC-based identity, stable subject mapping, tenant/workspace context, groups, and roles.

2. **Namespace / metadata / permission layer**  
   File tree, logical ownership, shares, access control, version references, public-link definitions, retention metadata, and audit event production.

3. **Blob/object storage layer**  
   S3-compatible storage for durable content bytes and version objects.

4. **Projection layer**  
   Search indexes, thumbnails, previews, notification projections, analytics summaries, and AI retrieval/indexing.

5. **Client sync layer**  
   Lightweight web and desktop access, sync sessions, pairing, resumable transfer logic, and conflict handling.

6. **Integration layer**  
   RustChat integration, webhooks, policy hooks, audit export, and future external ecosystem integrations.

## Detailed decisions

### D1. Object storage is the blob system of record

Durable file bytes and immutable versions will live in S3-compatible object storage.

This means:

- uploads produce blob objects and version objects
- downloads stream from object-backed durable content
- restores and exports are designed around object-backed durability
- lifecycle and replication strategy can be handled at the object layer

RustShare will not use a distributed POSIX filesystem as the primary product backbone.

### D2. Metadata and permissions are explicit and authoritative

Namespace structure, permissions, shares, public links, effective access, and file-to-version relationships will not be inferred from raw object structure alone.

RustShare will maintain an explicit metadata and permission authority.

This authority is the source of truth for:

- tree and path semantics
- group/user/role grants
- internal shares
- public-link policy
- revocation behavior
- audit triggers
- search authorization filtering
- AI authorization filtering

### D3. Tenant is the hard administrative and security boundary

The primary durable boundary is the **tenant**, not the user.

Implications:

- storage partitioning is tenant-oriented by default
- user ownership is represented in metadata inside the tenant
- shared content remains natural inside a tenant namespace
- future export/import tooling is tenant-scoped first

Per-user storage fragmentation is explicitly not the default product shape.
It may still exist in limited internal implementation details, but it is not the preferred administrative model.

### D4. RustChat integration is service-level, not database-level

RustShare and RustChat will share identity and group semantics, but they will not share a database or bypass each other’s authorization layers.

Integration will happen through:

- shared OIDC identity
- stable file references
- permission-aware previews and attachments
- event-driven updates and invalidation
- API-level operations for attach/share/open

RustChat must never become an authorization shortcut into RustShare.

### D5. AI is optional, separate, and permission-bound

AI and indexing capabilities are an optional subsystem, not the storage core.

They may provide:

- semantic search
- “ask this file/folder”
- summarization
- metadata extraction
- related-file suggestions

But they must obey the same effective permission model as ordinary file access.

No AI service is allowed to become an alternate source of unauthorized truth.

### D6. Rust is the default implementation language for core backend services

RustShare will continue to prefer Rust for core services that handle:

- auth-sensitive logic
- file movement and upload paths
- permission enforcement
- storage interaction
- integration boundaries
- audit generation

This is a deliberate choice to reduce avoidable memory-safety risk and keep the core platform maintainable for long-term infrastructure-heavy use.

### D7. The architecture must remain practical for the MVP

This ADR does **not** authorize a rewrite for purity.

The current MVP should be incrementally reshaped toward this architecture by:

- preserving valid working behavior
- reducing coupling step by step
- enforcing contracts with tests
- isolating storage, metadata, and integration concerns progressively

## Why this decision was made

### 1. File platforms have multiple durability concerns

A serious file-sharing platform has distinct concerns that should not be forced into one primitive:

- content bytes
- namespace
- permissions
- shares and revocation
- audit events
- previews and search indexes
- AI indexes and derived artifacts

Treating all of these as “just objects” creates hidden coupling.
Treating all of them as “just database rows” creates operational concentration and scaling pain.
Treating all of them as “just filesystem structure” leaks infrastructure semantics into the product.

### 2. Object storage fits file bytes better than databases or POSIX clusters

Object storage is the most natural home for:

- large durable blobs
- immutable versions
- export and backup alignment
- lifecycle policies
- replication portability
- cloud/private-cloud deployment flexibility

A file-sharing platform should expose a logical namespace, not force the user model to match raw storage internals.

### 3. Permissions must remain inspectable and testable

RustShare’s differentiation depends heavily on:

- clear sharing behavior
- predictable revocation
- chat/file permission consistency
- auditable access
- permission-aware AI

That requires an explicit authority for metadata and permissions, not ad hoc derivation.

### 4. RustChat integration needs boundaries

RustShare and RustChat should feel connected to users, but they should remain separate systems with well-defined contracts.

Shared databases would create:

- hidden coupling
- difficult migrations
- authorization ambiguity
- long-term scaling pain

### 5. The architecture leaves room for AI without making AI a dependency

AI is strategically useful, but the file platform must still work cleanly if indexing or AI is disabled.

That is only possible if AI is additive and bounded, not embedded into the core durability model.

## Consequences

### Positive consequences

- clearer separation between durable content and logical access semantics
- better long-term scalability for file bytes
- easier multi-tenant reasoning
- cleaner chat integration model
- safer path for search, previews, notifications, and AI
- improved portability across cloud and self-hosted environments
- better fit for auditability and policy enforcement

### Negative consequences

- higher architectural complexity than a monolith with one persistence primitive
- eventual consistency must be handled carefully for projections
- more moving parts for search, previews, and AI indexing
- requires disciplined contracts and observability
- migration from MVP shortcuts may take deliberate staged work

### Operational consequences

The team must invest in:

- strong contract tests
- audit event durability
- clear storage abstraction boundaries
- projection rebuild mechanisms
- observability around sync, uploads, revocation, and projection lag
- backup/restore verification

## Rejected alternatives

### Alternative A: PostgreSQL-only backend

**Rejected as the target architecture.**

Why it was rejected:

- it concentrates blobs, metadata, permissions, and event pressure in one operational system
- it makes large-file durability, restore, WAL growth, and lifecycle handling less natural
- it is viable for certain scales, but not the most realistic long-term product architecture for a multi-tenant file-sharing platform
- it solves “single source of truth” too literally while creating new scaling and operational pain

PostgreSQL may still exist in implementation details if needed, but it is not the desired blob strategy.

### Alternative B: Distributed POSIX filesystem as primary backbone

**Rejected as the default product shape.**

Why it was rejected:

- product semantics would become too coupled to infrastructure semantics
- object-style durability and version handling are more natural for this category
- multi-tenant isolation and cloud/private-cloud portability are less elegant as a primary product model

### Alternative C: Object-store only, no explicit metadata authority

**Rejected as too implicit.**

Why it was rejected:

- permissions, revocation, and sharing logic become harder to reason about
- namespace behavior risks becoming fragile or indirectly encoded
- AI and search authorization become more error-prone
- chat integration becomes less clean

### Alternative D: Per-user durable storage as the main product boundary

**Rejected as the default administrative model.**

Why it was rejected:

- it complicates natural collaboration inside a tenant
- it makes accounting, policy, and admin behavior less coherent
- it makes cross-user sharing and future tenant-wide governance harder

User ownership remains important, but inside a tenant-oriented product model.

---

## Migration guidance from the current MVP

This ADR does not require the MVP to be discarded.

The current implementation should be evolved in this order:

1. **Stabilize contracts**  
   Convert the contract document into integration, API, and end-to-end tests.

2. **Clarify the storage boundary**  
   Ensure file bytes and versions are cleanly separated from namespace and permission logic.

3. **Normalize tenant-centric metadata**  
   Make tenant the hard boundary and avoid accidental user-island behavior unless explicitly needed.

4. **Harden RustChat integration seams**  
   Move toward stable APIs, event hooks, and permission-checked references.

5. **Introduce projection discipline**  
   Search, previews, AI indexing, and notifications must become explicit secondary views.

6. **Preserve lightweight clients**  
   Client design should remain thin, deterministic, and not absorb backend complexity.

---

## What this ADR means in practice

Engineering should assume the following are true going forward:

- blob durability belongs in object storage
- namespace and permissions are explicit system concerns
- search and AI are projections, not sources of truth
- RustChat integration happens through identity, APIs, and events
- tenant is the main security and administrative boundary
- Rust remains the preferred language for core services
- incremental alignment is preferred over rewrites

---

## Decision summary

RustShare will move forward as a **tenant-centered, object-store-backed, metadata-authoritative, service-oriented platform** with **bounded RustChat integration** and **optional permission-aware AI subsystems**.

This is the most realistic design for building a survivable, self-hostable, technically credible file-sharing platform in 2026 without overfitting to either database purity or infrastructure leakage.
