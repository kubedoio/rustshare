## Context

Evidence is the five Phase 4.0 source audits, the **executed** negative-test run report (`docs/audits/2026-10-13-phase4-0-tenant-isolation-negative-tests.md`: 36/36 probes as-asserted, one deliberate fail-closed 42501, plus live HTTP reproduction), the consolidated evidence matrix (`docs/audits/2026-10-13-phase4-0-tenant-isolation-evidence-matrix.md`, 71 rows), the product issues, and direct re-verification of the cited lines. All findings below are current behavior, not intended architecture. Where a source audit and the executed evidence disagree, the executed evidence wins; the one such disagreement inside this ADR's scope (`F4`) is recorded in D8.

**Tenant identity is real but is never called "organization".** `tenant_id UUID NOT NULL DEFAULT '00000000-…'` exists on `users`, `folders`, `files`, `shares`, `file_versions`, `notifications`, `user_groups`, `file_thumbnails` (`backend/migrations/20260329170001_add_tenant_id_to_tables.sql:4-33`), `user_sessions` (`20260329200001`), `invite_tokens` (`20260402000002:3`), and the calendar tables (`20261001090000_create_calendar_tables.sql:3,38`). No organization entity exists anywhere in the backend (repo-wide search of `backend/server/src` and `backend/crates` finds only a UI label at `oidc_runtime.rs:499`).

**Request organization context comes from the credential's row, not the request.** Bearer JWTs resolve `tenant_id` from `users` (`backend/server/src/handlers/extractors.rs:65-78`); web sessions from `user_sessions` (`backend/server/src/web_session.rs:24-70`, used at `extractors.rs:152-164`). The JWT `tenant_id` claim is ignored on HTTP paths but *is* the tenant for WebSocket identity (`backend/server/src/handlers/ws_auth.rs:46`). `X-Tenant-ID` exists only on the public share and public chat-unfurl routes (`handlers/public_shares.rs:37-57`; `handlers/chat_integration.rs:26`, read at `:164`, where the authenticated unfurl variant instead takes `auth.tenant_id`, `:104-118`). Isolation is otherwise application-level `owner_id`+`tenant_id` predicates; RLS is decorative (postgres-rls audit F5, F6).

**Workspace does not exist as a model.** No `workspaces` table in any migration. `note_index_chunks.workspace_id` was backfilled from `tenant_id` as an explicit compatibility shim (`backend/migrations/20260723000000_note_index_acl_columns.up.sql`). `File::workspace_id()` returns `tenant_id` (`backend/crates/core/src/domain/file.rs:75-77`). Search builds `RetrievalPrincipal { workspace_id: Some(tenant_id) }` with the comment "each tenant maps to exactly one workspace" (`backend/crates/core/src/services/ai_service.rs:190-197`, `:258-265`). `POST /api/v1/memory/ask` documents "Must equal the authenticated tenant/workspace in the current 1:1 model" (`handlers/ask_workspace.rs:18`). There is no workspace membership, workspace role, or group→workspace mapping (groups-workspaces audit §2).

**Nil is the runtime default organization, not a legacy-only value.** `RUSTSHARE_DEFAULT_TENANT_ID` defaults to the nil UUID (`backend/server/src/bootstrap.rs:715-718`); seed, OIDC (`oidc.rs:591-623`), SCIM v2 (`scim_v2.rs:743` ff.) and admin-created users all land there, and admin/SCIM-created groups land there too because their INSERTs omit `tenant_id` (tenant-identity audit F2, F3, F8; groups-workspaces audit F3). Nil is simultaneously the permissive RLS sentinel (`20260507220652_fix_rls_to_allow_nil_default.sql:11-35`).

**Two surfaces are installation-global by construction, and one is a confirmed exploit.**
- SCIM v1/v2 share one environment bearer token with no organization scope, and their queries are unscoped: `FROM users WHERE 1=1` (`handlers/scim_v2.rs:141-142`), get/PATCH/DELETE by bare id (`:209`, `:361-398`), v1 lookup/disable by global `external_id` (`handlers/scim.rs:321-341,431-456`), v1 accepts a client-supplied `tenantId` and creates the user in any tenant (`backend/crates/core/src/services/scim_service.rs:56-57,236,283`). This is tenant-identity audit F1, classified **confirmed access bypass** and backed by an executed probe (matrix `P4-01`: an unscoped SCIM v2 list returned rows spanning two tenants).
- Every `admin/*` handler takes the installation-wide `AdminUser` extractor (`handlers/extractors.rs:277-308`) and scopes nothing to a tenant; `list_admin_users` is cross-tenant (`admin/users.rs:158-311`); `create_admin_user` omits `tenant_id` (`admin/users.rs:371-385`); uniqueness pre-checks are global (`admin/users.rs:329-350`). F2 and F3.

**Administration has no organization scope to build on.** The only admin primitive is the installation-wide `users.is_admin` boolean (`20260317000002_create_users_table.sql:8`); no migration defines any role column or role table (repo-wide grep). Verified positive: no admin handler reads file or note bodies (groups-workspaces audit §3), so "administration does not imply content access" is already true for the global admin.

**Identity uniqueness is directory-global for usernames and external IDs.** `users.username VARCHAR(255) UNIQUE` (`20260317000002:4`), `users.external_id TEXT UNIQUE` and `user_groups.external_id TEXT UNIQUE` (`20260328000001`), while `users.email` is unique per tenant only, case-insensitively (`20260617160001_add_users_email_lower_index.sql:10-14`). The invite pre-check is a global, case-sensitive `WHERE email = $1` (`invites.rs:269-272`), producing F7.

**Product requirements.** #333 (pilot epic, ~100 users, explicitly no customer-specific domain model), #330 (groups, bounded roles, workspace membership, "cross-tenant membership is rejected", "organization administration must not grant implicit access to workspace content"), #331 (tenant-scoped bulk onboarding/offboarding), #332 (organization-scoped administrative audit).

## Decision

**D1. An organization *is* a tenant; `tenant_id` is the organization identifier.** Phase 4.0 introduces no `organizations` table and no organization column anywhere. The organization of a principal is `users.tenant_id`; of a resource, that row's `tenant_id`; of a session, `user_sessions.tenant_id`; of a group, `user_groups.tenant_id`. Rationale: every authorization predicate, repository signature, share filter, session row, invite token and calendar row already carries `tenant_id`; adding a parallel organization entity would require a second boundary, a join on every read path, and a bidirectional mapping with no source of truth — the exact "parallel lifecycle and mapping state" ADR-0038 already rejected. Whether an organization needs a name or settings is a configuration/instance concern, not user data; Phase 4.0 stores no organization metadata.

**D2. A workspace is the organization in Phase 4.0 (1:1), stated explicitly rather than implied.** No `workspaces` table is added. Consequences that are binding decisions:
- `workspace_id` is never accepted from a client as an authorization input. Where a request carries it (for example `POST /api/v1/memory/ask`), it must equal the authenticated organization or the request is rejected; it must never widen or redirect scope.
- Writers of the index ACL must set `workspace_id` from the *resource's* organization (`File::workspace_id()` is that identity today, `backend/crates/core/src/domain/file.rs:75-77`), never from the requester's.
- No production ACL **writer** may emit a `workspace:<uuid>` principal into a chunk's read principals while the 1:1 model holds, because `workspace:X` and `tenant_id = X` would then mean the same thing through two mechanisms. The only production writer is `resolve_read_principals`, which emits only `owner:`/`user:`/`group:` principals (`backend/crates/core/src/services/permission_resolver.rs:699,709,721,769,782`), so the `visibility = 'workspace'` arm never fires. This is a **writer-side prohibition**, not a claim that the mechanism is test-only: the principal and visibility types are production code (`IndexPrincipal::Workspace` at `backend/crates/core/src/services/ai/indexing.rs:86,96,117`; `IndexVisibility::Workspace` at `:24`), `RetrievalPrincipal::to_index_principals` expands a `workspace:<uuid>` string in production (`:159-161`), and both production search paths set `workspace_id: Some(tenant_id)` (`backend/crates/core/src/services/ai_service.rs:191-197`, `:260-266`). The retrieval-side workspace filter (`workspace_id = $5`, `pg_vector_store.rs:180-248`) therefore matches nothing today because no production note path produces `visibility = 'workspace'` (note visibility is `private|public`, `note_service.rs:97-108`). Introducing a workspace-aware writer requires lifting the 1:1 rule in a reviewed decision first.
- Explicit trigger to revisit: a product requirement for more than one workspace per organization. Until then, ADR-0038 decision 2's workspace model is **deferred and refined**, not fulfilled: its tenant-bound membership rule is kept as a statement about the organization (D3, and ADR-0041 D2/D3 for group membership), and the audit trail must record that workspace existence/membership is unimplemented.

**D3. Principal membership in an organization is `users.tenant_id` and nothing else.** For Phase 4.0 a user belongs to exactly one organization. Membership is changed only by administrative user operations inside that organization (#331), never per request. A request's organization must equal the credential's organization *and* the user's current `users.tenant_id`; a credential whose recorded tenant no longer matches the user row fails closed (this closes the session/claim drift channel described below). Cached membership does not outlive revocation (ADR-0038 decision 6): resolution is live per request (`backend/crates/infrastructure/src/repositories/permission_resolver.rs:160-175` — note that two files share this name; the other is the core-service resolver), and no membership may be cached across requests.

Credential-specific rules, since the three credential forms do not agree today:
- Stateless JWT: the `tenant_id` claim is not authoritative on any path. HTTP already ignores it (`extractors.rs:65-78`); the WebSocket path must stop trusting it (`ws_auth.rs:46`) and must validate the claim against `users.tenant_id` (it already loads the row to check `disabled_at`, `ws_auth.rs:69-84`).
- Server-side sessions: `user_sessions.tenant_id` must equal `users.tenant_id` at resolution; on mismatch the session is invalidated rather than honored (`web_session.rs:24-70` currently checks only `disabled_at`).
- The JWT tenant claim remains a token-carried hint for logging/display only. No organization may ever be selected by `X-Tenant-ID`, request bodies, or connection state on an authenticated route.

**D4. The default organization, and the interface to legacy nil-tenant data (details belong to ADR-0043).** The default organization of a deployment is `RUSTSHARE_DEFAULT_TENANT_ID`; for a fresh single-organization deployment that is the nil UUID. The interface this ADR fixes:
- Nil is a legal organization identifier meaning "the deployment's default organization". It is not "unknown", not "any", and not a wildcard.
- Every creation path must write an explicitly resolved organization. Nil may be written only when the resolved organization *is* the default organization. Where the resolver cannot produce an organization, creation fails closed with a client error; the nil column default must never be the effective source of a new row. This immediately forbids the current `admin/users.rs:371-385`, `admin/groups.rs:183-185`, `scim.rs:490`, `scim_v2.rs:496` behavior.
- No migration or runtime rule may infer a non-default organization for a nil-tenant row from a name, an email domain, a group, or a user (ADR-0038 migration constraints, reaffirmed). Nil rows stay in the default organization until an operator-approved mapping exists (ADR-0043).
- When the default organization is non-nil, nil-tenant rows are legacy rows outside it, and every strict equality rule in this ADR and ADR-0041 makes them fail closed rather than grant access.
- **Direction of the nil risk, corrected by executed evidence.** The previously asserted chain — a nil-tenant user in a nil-tenant group reaching a real-tenant file through a nil-tenant share row — is **refuted**: with resolution keyed on the file's tenant, the membership lookup requires `users.tenant_id = <lookup tenant>`, so a nil-tenant user never resolves the group (negative-test report case (e), probes 13–14; matrix `P4-14`, `#287-R17`). What is live is (i) resolution *within* the nil organization, which a default deployment manufactures through the API (probe 15, DIRECT), and (ii) the reverse direction — a real-organization principal reaching **nil**-tenant resources through nil-tenant share rows (probe 16; same root cause as the C3 asymmetry). Nil-tenant rows must therefore never be treated as a path into real-organization content, and the strict-equality rules must cover both directions.

**D5. Cross-organization restrictions: every management surface gets an organization scope.**
- **SCIM (fixes F1).** The SCIM bearer token is bound to exactly one organization: a configuration value (`RUSTSHARE_SCIM_TENANT_ID`, defaulting to `RUSTSHARE_DEFAULT_TENANT_ID`) supplies the scope for the token. Every SCIM read, count, update, disable, delete and group-membership operation carries that tenant predicate; SCIM v1's request-supplied `tenantId` must equal the scope or be rejected (`400`) and SCIM v2 accepts no tenant input at all. User and group creation writes the scoped organization explicitly. SCIM group-member references resolve inside the scoped organization only. A leaked SCIM token then yields cross-org data exposure only if it is also the token for that organization.
- **Administration.** `AdminUser` keeps its meaning (installation operator, cross-organization, no implicit content access), but no organization data may be returned without a resolved organization scope. The default scope for user/group administration is the actor's own organization. An installation operator may request a different organization explicitly; that mode must be a distinct, audited request (not the default), and every response must report the organization it was scoped to. Organization administrators (D7) are limited to their own organization by construction.
- **Public links.** Unchanged and reaffirmed: token-scoped, tenant-derived, self-contained (`0031-tenant-isolation-share-links-and-rls.md` as tested by `backend/tests/contracts/tenant_isolation_contract.rs`). Public-link *creation* must additionally verify `resource.tenant_id == requester tenant` (share-creation rule, ADR-0041 D2).

**D6. Identity uniqueness stays directory-global in Phase 4.0.** `username` and `external_id` remain installation-wide unique; multi-organization deployments therefore require directory-unique usernames. Rationale: login accepts a bare email/username (`auth.rs:93-113`), the invite flow sets `username = email` (`invites.rs:288-298`), and per-organization uniqueness would require both a schema change and an unambiguous organization selector on every unauthenticated login request. The constraint must be documented in the operator runbook rather than discovered at user-creation time. Per-organization uniqueness is a prepared, lossless follow-up (drop the global unique constraint, add a composite one) and is listed for human approval rather than decided unilaterally.

**D7. `users.is_admin` and organization administration stay distinct.**
- `users.is_admin` continues to mean **installation operator**: cross-organization, break-glass, and — verified — with no implicit access to any file or note body. It is not extended, not tenant-scoped, and not granted automatically by any new mechanism.
- **Organization administrator** is a new, explicit, tenant-scoped grant stored in one additive table, `organization_administrators(user_id, tenant_id, granted_by, granted_at, revoked_at)`, with the primary key on `(tenant_id, user_id)`. A new extractor (`OrganizationAdmin`) resolves it per request from `users.tenant_id` + an active grant; `is_admin` does not satisfy it. Rationale for a table rather than a flag or a group: a user's organization membership is single-valued (`users.tenant_id`) so no column is needed for membership, but administration is a *grantable* fact that must be independently revocable and auditable, and reusing an ACL group would make a mutable, user-visible, globally-named container into a privilege source.
- Bounded role vocabulary for Phase 4.0: `member` (implicit in `users.tenant_id`) and `administrator` (the grant above). No other organization role is introduced, and no school-, class-, student- or customer-specific role exists.
- Bounded capability set for an organization administrator within its organization: invite/create/disable members; create, rename and archive groups; add/remove group members; view membership and effective-access explanations; view organization-scoped audit events (#332). Explicitly outside its capability set: any private file/note content it does not own or hold a share for, other organizations, installation configuration, applications/templates/webhooks/workflows, and user impersonation.
- The hard constraint is preserved mechanically, not by convention: organization administration adds no path into the content resolver. There is no "admin sees everything" code path to remove because none exists; the invariant (A4 below) and its negative test keep it that way.
- Grant creation is restricted to an installation operator for Phase 4.0 (no privilege proliferation, no bootstrap chicken-and-egg). Existing `is_admin` holders are **not** auto-granted organization administrator: ADR-0038's no-inference constraint applies, and the installation operator remains available without the grant.

**D8. Principal lifecycle and disable revocation: database-level, with one residual JWT gap.** Credential revocation on disable is **already guaranteed for every writer at the database level** and needs no new per-handler code: migration `backend/migrations/20261003090000_revoke_credentials_on_user_disable.sql` installs the `AFTER UPDATE OF disabled_at` trigger `users_disable_revokes_credentials`, which deletes the principal's `user_sessions` rows and sets `device_tokens.revoked_at` for every writer "including SCIM and future administrative paths" (migration comment). The SCIM handlers perform no explicit revocation of their own (`scim.rs:431-456`, `scim_v2.rs:360-398`) and do not need to. Executed: after the exact SCIM-shaped `UPDATE users SET disabled_at = NOW()`, `user_sessions` = 0 and the live device token is revoked; a pre-existing device token is rejected with `401` both while disabled **and** after re-enable (negative-test report §4(h), case (h); matrix `P4-10`; regression-asserted by `backend/tests/user_disable_credential_revocation_test.rs`). The tenant-identity audit's **F4 ("re-enable resurrects device tokens") is refuted at this baseline** and must not be cited as evidence anywhere.

Decision: revocation parity comes from the trigger, not from duplicating revocation in each entry point. The trigger is the revocation contract, so any future disable path that does not pass through `UPDATE users.disabled_at` (bulk SQL that bypasses the column, or a hard delete) must be reviewed against it explicitly, and a test must keep the property pinned.

Residual gap, genuinely open: a **stateless JWT** issued before the disable is honoured again after re-enable until its `exp` (default 24 h, `config.rs:155-157`), because `resolve_bearer_token` has no token-version or session-linkage check (`extractors.rs:60-79`). This is the same class as the admin password-reset / logout gap (tenant-identity F5; matrix `P4-11`) and is already tracked as issue #215; the existing suite asserts it deliberately as a labelled change detector. Whether it is in scope for this gate is an open decision (approval item 9); the recommendation is to **defer** the fix — a token-version column or session linkage is a credential-lifecycle change orthogonal to organization identity — while recording the gap and bounding invariant A6 accordingly. (Credential lifecycle, not group semantics; recorded here because it is identity lifecycle.)

**D9. Nothing in this ADR activates garbage collection or orphan reconciliation.** No decision here enables, implies, or depends on production GC or orphan reconciliation. Both remain disabled by default and out of scope.

## Relationship to ADR-0038 (decision by decision)

- **Decision 1 (tenant = institutional boundary): extended.** Affirmed as binding, and extended to the two surfaces where it is violated today (SCIM, `admin/*`), with the "one tenant = one organization" claim made explicit as D1. Also refines the nil question: nil is the default organization, not an implicit boundary failure.
- **Decision 2 (workspace distinct, tenant-bound): refined and deferred.** The tenant-bound rule is kept and applied to organization membership (D3, D5). Workspace existence/membership is *not* implemented; D2 states the 1:1 identity explicitly, forbids client-supplied workspace identity, and names the trigger for revisiting. ADR-0038 decision 2 is therefore not yet satisfied.
- **Decision 3 (installation admin vs organization admin): extended and implemented at the identity layer.** The first half is confirmed as-is; the second half is realized as the `organization_administrators` grant plus `OrganizationAdmin` extractor (D7), with the "no implicit access to private resources" clause preserved as an invariant and a test, not a convention. The open half is the restricted who-may-grant question (item 2 of the approval list).

- **Decision 6 (additive, explainable grants; immediate revocation): carried, partially implemented.** Immediate revocation is already true for content and is preserved; explanation of grant paths is decided in ADR-0041 D6. No new authorization authority is introduced by this ADR.

- **Approval required: affirmed and extended.** ADR-0038's approval requirement carries over: this gate closes only with the explicit approvals in the list below, and no SCIM scoping, admin scoping, or strict-equality change proceeds while they are unresolved.
- ADR-0038 remains **Proposed and in force**; it is extended and refined here, not superseded.

## What needs no schema migration, and what does

**No schema change required (code and configuration only):** organization identity (= existing `tenant_id`); workspace identity; SCIM organization scoping (predicates + one configured scope + rejecting client `tenantId`); admin-handler organization scoping and the cross-org opt-in mode; the WS/session tenant-consistency checks; the requirement that every creation path resolve an organization explicitly (writes an existing column); the creation-time equality checks in ADR-0041 D2; and the creation-time organization resolution that makes the nil column default unreachable. Credential revocation on disable needs no change here: it is already enforced at the database level by the `users_disable_revokes_credentials` trigger (D8).

**Schema changes proposed by this ADR (both additive):** (1) `organization_administrators` as in D7, no backfill, no data migration, no constraint on existing tables; (2) a nullable `admin_actions.tenant_id` so administrative actions become organization-attributable (#332 owns that table; stated here as a requirement, not as this ADR's change).

**Not this ADR's:** PostgreSQL roles, RLS enabling/FORCE, connection-level identity plumbing (ADR-0042); nil-tenant inventory, backfill or mapping (ADR-0043). Neither is a prerequisite for the code-only items above.

**Migration cost and rollback.** Code-only items are revertible by redeploy with no data state to unwind. The `organization_administrators` table is inert until the extractor is enforced, so it can ship ahead of enforcement. No proposal here rewrites existing rows, so there is no destructive rollback scenario. The one operational cost is the pre-flight inventory for legacy mismatched rows (below) and the deployment decision for `RUSTSHARE_SCIM_TENANT_ID`.

**Compatibility with existing deployments.** A single-organization deployment with `RUSTSHARE_DEFAULT_TENANT_ID` left at nil and SCIM unconfigured keeps working unchanged: all users, groups, resources and shares are nil-tenant and consistent, SCIM's scope resolves to nil, and the installation operator keeps its current surface. A deployment with a non-nil default organization, or with admin/SCIM-created nil rows, must run the inventory before upgrading (see Consequences).

## Security invariants

- **A1 — Organization context is derived, never supplied.** For every authenticated request the organization comes from the credential row and must equal the principal's current `users.tenant_id`. No header, body field, JWT claim, or reused connection may select an organization.
- **A2 — No cross-organization disclosure.** No listing, count, lookup, error message or existence check may reveal principals, groups, or resources of another organization, except an explicit, audited installation-operator cross-organization request.
- **A3 — Explicit organization on creation.** Every principal or group creation names an organization that is explicitly resolved; the nil default is never the effective source of a new row.
- **A4 — Administration confers no content access.** Neither installation nor organization administration grants read or write access to file or note content; content access is decided only by ownership, explicit shares, and folder ancestry through the single `PermissionResolver`.
- **A5 — One boundary, two evaluators, one answer.** Where the resource-keyed resolver (Files service) and the requester-keyed source authorizer decide the same request, they must agree; a mismatch fails closed (deny). The notes pattern (`resource.tenant_id == principal.tenant_id` checked at the service boundary, `note_service.rs:1361-1363`) is the required shape.
- **A6 — Disabled means revoked, with one documented exception.** Every disable path revokes server-side credentials (web sessions and device tokens) at the database level, so a re-enabled principal cannot use them (executed: matrix `P4-10`, negative-test case (h)). The exception is the stateless JWT, which remains usable until `exp` after a re-enable; it is bounded by the 24 h default lifetime, is a tracked gap (issue #215, approval item 9), and must never be presented as closed.
- **A7 — Token tenant drift fails closed.** A credential whose recorded organization no longer matches the principal's row is rejected, not silently re-scoped.

## Negative tests required by this ADR

Existing suites to extend: `backend/tests/contracts/tenant_isolation_contract.rs`, `backend/tests/admin_users_test.rs`, `backend/tests/admin_groups_test.rs`, `backend/tests/invites_test.rs`, `backend/tests/user_disable_credential_revocation_test.rs`, `backend/tests/pilot_group_scope_inventory_test.rs`, `backend/server/tests/websocket_*`.

1. **Cross-organization management is impossible.** A SCIM token scoped to organization A cannot list, read, patch, disable, or delete principals or groups of the default organization or of B; SCIM v1 with a `tenantId` different from the token scope is rejected; SCIM-created users and groups land in the token's organization.
2. **Admin scoping.** An organization administrator's list/get/update targeting another organization returns the same non-disclosure result as a nonexistent id; an installation operator without the explicit cross-organization mode does not receive other-organization rows either.
3. **Default-organization compatibility.** With `RUSTSHARE_DEFAULT_TENANT_ID` nil, seed, OIDC, SCIM and admin creation all produce rows in the default organization and existing nil-tenant behavior is unchanged.
4. **No implicit nil creation.** A creation request with no resolvable organization is rejected; no new row appears with a nil tenant that is not the default organization.
5. **Disabled user cannot regain access through server-side credentials (regression; already green as a database property).** A disable must leave no `user_sessions` row and must set `device_tokens.revoked_at` for every writer, including the SCIM-shaped `UPDATE users SET disabled_at` (executed baseline: negative-test report case (h); matrix `P4-10`; `backend/tests/user_disable_credential_revocation_test.rs`). The suite must also keep asserting, explicitly and labelled, the residual stateless-JWT exception of D8, so it cannot silently drift back into an unstated claim (approval item 9).
6. **Token tenant drift.** A session or WebSocket credential whose tenant differs from the user's row is rejected.
7. **Administration does not read content.** An organization administrator (and the installation operator) requesting a private file or note owned by another member of the same organization, or by another organization, is denied, and unified search returns no candidate from it. This is the explicit negative test for the milestone's "org admin cannot implicitly access private content".
8. **Same-decision test (A5).** A seeded share/environment that the Files resolver and the source authorizer evaluate differently must yield deny, not a split decision (the C3 probe; ADR-0041 D2 supplies the creation-time fix).
9. **No context leak across pooled connections.** Sequential requests by different principals must never observe the other's organization from cached or connection-scoped state. ADR-0042 owns the SQL-level proof; this ADR owns the requirement that identity is re-derived per request and that `app.*` connection settings are never an authorization input.

## Alternatives considered

- **Introduce an `organizations` table with `tenant_id` as a foreign key.** Rejected for Phase 4.0: it creates a second boundary and a parallel lifecycle with no source of truth, forces a join on every authorization predicate and every repository signature, and no requirement in #330–#333 demands organization metadata. Revisit only for a concrete requirement (organization rename/history, org-level settings, per-organization billing).
- **Introduce a `workspaces` table now.** Rejected: no consumer needs more than one scope per tenant (search, ask, note index, chat workspace mapping all key on tenant), the backfill would have no authoritative source, and it would put a second unverifiable identifier on every resource. Trigger stated in D2.
- **Reinterpret existing `tenant_id` values (for example map nil to a newly created organization).** Prohibited by ADR-0038's migration constraints and unnecessary; nil handling is ADR-0043's decision.
- **Derive the organization for legacy rows from a display name, email domain, or group name.** Rejected: names and emails are mutable and collide across tenants; the invite case-variant defect (F7) shows exactly this class of ambiguity.
- **Use an ACL group (for example a group named "Admins") as the organization-administrator role.** Rejected: group names are globally unique and mutable, groups are user-visible ACL containers, group membership is not tenant-validated today (ADR-0041 D1), and conflation would create a privilege-escalation path from share administration into administration.
- **Tenant-scope `users.is_admin` by adding a column to `users`.** Rejected: installation operation is genuinely cross-organization, and merging the two roles destroys the operator/member separation ADR-0038 decision 3 requires.
- **Keep SCIM as an installation-trusted token and rely on operator discipline.** Rejected: F1 is a confirmed cross-tenant exploit, not a hardening gap.
- **Make usernames and external IDs unique per organization now.** Deferred (D6): it costs a schema change plus an organization selector on unauthenticated login, with no Phase 4.0 requirement.

## Consequences

- The pilot's "one tenant = one organization" claim becomes true under a leaked or misconfigured SCIM token and under a non-nil default organization, at the cost of SCIM configuration and per-surface scoping work.
- Workspace functionality promised in ADR-0038 decision 2 is explicitly absent. UI and API must not imply workspace membership exists; `workspace_id` stays a derived identity, and the `permission-aware-indexing-contract.md` sentence "it must never be silently defaulted to `tenant_id`" must be amended to describe the documented 1:1 identity (contract edit, see approval item 6).
- Existing mismatched artifacts become unusable rather than silently privileged: nil-tenant groups with non-nil members, groups created by admin/SCIM while a non-nil default organization was configured, and admin-created users outside the default organization. These populations are exactly what `scripts/pilot-group-scope-inventory.sql` and `backend/tests/pilot_group_scope_inventory_test.rs:37-300` count. The inventory must run, and its result must be accepted by an operator, before the strict equality rules land (ADR-0043 supplies remediation).
- Organization administration is deliberately thin: no content capability, no automation, no delegation, and grants issued only by an installation operator. Expected operational friction is accepted in exchange for a small attack surface at ~100 users.
- Adding a role table means one more thing to audit; the audit-log schema and query surface are #332's, and this ADR only requires that organization scope and actor be attributable.

## Decisions requiring human approval

1. **Confirm organization = tenant with no `organizations` table, and workspace = organization for Phase 4.0 with the stated revisit trigger.** Recommended: yes. This is the load-bearing choice for every other Phase 4.0 decision.
2. **Approve the single additive table `organization_administrators`, that `is_admin` does not satisfy it, that existing `is_admin` holders are not auto-granted, and that only an installation operator may create or revoke the grant in Phase 4.0.**
3. **Approve the SCIM single-organization binding mechanism and its failure mode**: `RUSTSHARE_SCIM_TENANT_ID` (falling back to `RUSTSHARE_DEFAULT_TENANT_ID`), client-supplied `tenantId` rejected. Recommended: yes; confirm IdP integration impact, since a tenant-scoped SCIM token cannot manage more than one organization in this phase.
4. **Decide whether the installation operator retains an explicit cross-organization listing mode in `admin/users`.** Recommended: yes, as a distinct audited request rather than the default; the alternative (removing it) increases operator effort with no security gain.
5. **Confirm `username` and `external_id` stay installation-globally unique in Phase 4.0.** Recommended: yes; document the directory-wide uniqueness requirement in the deployment runbook.
6. **Approve the security-contract wording edits implied here** (the `workspace_id` sentence in `docs/contracts/permission-aware-indexing-contract.md`, and the `min_acl_versions` wording in ADR-0041 D9). Recommended: yes; documentation-only, no code path changes.
7. **Decide whether nil-tenant rows outside a non-nil default organization are remediated by ADR-0043's migration or by operator action.** Recommended: ADR-0043 owns the mapping; this ADR keeps runtime strict equality so nothing is granted by accident in the meantime.
8. **Confirm the ADR numbering and the index rows**: the planned `0039` was unavailable, so this ADR is `0040` and its companion is `0041` (matching the sibling `0042`/`0043`). `docs/adr/README.md` now contains the index rows for all four (`0040`–`0043`), added by the orchestrator since this ADR may not edit existing documents; approval covers their titles and status wording, which are being matched to the ADR H1s and status lines.
9. **Decide the residual stateless-JWT gap (D8)**: after a disable and re-enable cycle, a JWT issued before the disable works again until `exp` (default 24 h) because there is no token-version or session-linkage check. Recommended: **defer the fix out of this identity ADR** — it is a credential-lifecycle change orthogonal to organization identity — while keeping invariant A6 explicitly bounded and the existing change-detector test in place; if the security owner prefers to close it inside Phase 4.0, it becomes a separately scoped change with its own schema decision (token version or session linkage).
