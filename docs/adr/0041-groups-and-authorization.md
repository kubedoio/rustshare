# ADR-0041: Groups and Organization Authorization

Status: Proposed — human architecture and security approval required; no implementation authorized.
Date: 2026-10-13; corrected 2026-10-15.
Historical baseline: `1ec2ea7a887ee0ab79d7d8ce525a0e5a76e0109e`; current source review: main `cb31eff9`.

## Problem, existing behavior and product requirement

Elembra needs understandable collaboration permissions and immediate revocation without a universal policy framework. The [historical evidence matrix](../audits/2026-10-13-phase4-0-tenant-isolation-evidence-matrix.md) and [executed negative-test report](../audits/2026-10-13-phase4-0-tenant-isolation-negative-tests.md) remain unchanged evidence of their stated baseline. Their observations are not current findings after fixes merge. The [post-hotfix source supplement](../audits/2026-10-15-phase4-0-post-hotfix-verification.md) reconciles #361 (SCIM), #362 (publication) and #365 (tenant-safe groups). Source reading and merged tests are not deployment or newly executed evidence.

Groups already carry `tenant_id`; membership derives tenant from the group and user. #365 adds service/roster guards, but infrastructure `get_user_group_ids` still filters the user's tenant without joining the group's tenant: strict legacy group-expansion equality remains implementation work. Files/Notes use ownership, direct/group shares and folder ancestry, but share management retains a second evaluator. Effective permission sources exist internally; exposing explanations and ensuring index-refresh mutation parity remain implementation work. Index projections are candidate filters, with live source reauthorization the security boundary.

## Selected decisions and rejected alternatives

**D1 — Tenant-bound groups.** Each group has exactly one authoritative `user_groups.tenant_id`. Every creation path explicitly writes resolved tenant; membership requires user/group tenant equality. Reads and expansion filter group and member tenant. Legacy mismatched rows remain preserved but grant nothing; preserving storage is distinct from accepting membership for authorization. Nil is a legal tenant identifier, never an alias for whichever organization is configured by default (ADR-0043). Nested groups and a redundant membership tenant column are rejected: neither is needed for the institutional workflow, and both add consistency or traversal problems.

**D2 — Sharing authority is separate from recipient membership.** Validate `resource.tenant_id == share.tenant_id == recipient_group.tenant_id == principal.tenant_id` at creation and resolution. Then require the sharer's resource grant authority; group membership alone never permits sharing. An authorized owner or resource Admin need not join the recipient group. Missing/foreign recipients and foreign resources deny without disclosing tenant identifiers or existence. Non-Admin delegated-sharing behavior must remain bounded by the existing resource contract and never grant a permission the sharer lacks; any expansion requires separate approval. Public-link creation also requires requester/resource equality. #365 implements the relevant tenant guards; do not reschedule them as new features. Current #365 guards still distinguish missing and foreign groups through 404/403 behavior; uniform non-disclosure is a remaining implementation/release gate, not a shipped guarantee. Security owner must review normalized externally observable behavior and its negative tests before claiming this invariant.

**D3 — Application-owned authorization.** Platform Core provides principal, tenant, group and global Application-grant context. Resource-owning Applications authorize their resources. Files/Notes consolidate competing evaluation into their existing PermissionResolver, with requester/resource equality checked before resolution; the source authorizer and HTTP service must agree. Mail, Buzz Chat, Memory, Agents and future Applications retain their own authorization contracts. Buzz keeps its independent engine and signed communication boundaries. Universal Files authorization, generic ABAC and parallel evaluators inside the same resource family are rejected.

**D4 — Membership and references convey no implicit grant.** Organization, group and future workspace membership affect which explicit grants may resolve; they are not content grants. A ResourceRef is a reference, never authority. Memory and Agents reauthorize the owning source before materializing protected content into a response, index-derived context or model prompt. Search hits and general Agent execution permission are insufficient. ADR-0040 alone defines compatibility-only workspace identity and future workspaces; this ADR introduces no workspace membership or role API.

**D5 — Publication is an exposure operation.** Both publication and the explicit unpublication operation require resource owner or Admin-level resource permission. View and Edit alone deny, before sidecar/index mutation. #362's `note_service.rs::toggle_visibility` enforces tenant equality and resolver Admin checks for both directions; ownership succeeds through the resolver. A future explicit publish capability is deferred until demonstrated demand.

**Open security gate:** source comments preserve an Edit-sidecar availability limitation: client-writable metadata becoming private can cause public reads to deny. This does not permit publication, but prevents claiming owner/Admin authority over every route that suppresses public availability. Security owner must explicitly accept the bounded residual for the pilot or require a separately reviewed implementation and tests. No documentation-only correction closes this gate.

**D6 — Additive grants, live revocation and explanations.** Effective permission is the highest applicable live ownership/direct/group/inherited permission. Removing one path leaves other valid paths; removing the final path denies on the next authorization check. Group deletion revokes derived access without deleting content. In-flight bytes already delivered cannot be recalled. Explanations reuse the actual decision's PermissionSource, with share/group/ancestor identifiers only where the caller may inspect them; they do not perform a competing evaluation and cannot become client authorization input. Organization administrators gain no private content or grant enumeration merely from their role.

**D7 — Candidate ACL refresh and operational simplicity.** Keep live source reauthorization mandatory even with stale projections. Membership/delete/SCIM/bulk mutation paths must share refresh behavior; bulk refresh coalesces per affected group. Existing historical C4 nil-group/non-nil-share setup is a labelled legacy regression fixture, not a state current APIs necessarily produce after #365. Refresh must preserve each resource's tenant check; never infer tenant from the group to repair legacy records. Best-effort refresh may delay discoverability and requires monitored failures and an operator retry procedure. A durable queue is deferred until measured lag/loss makes the simple retry approach inadequate. Stale principals may remain in the index temporarily but cannot grant content. `min_acl_versions` is a backstop only for callers supplying a floor; production retrieval currently relies on live reauthorization, not an armed floor.

**D8 — Administration and names.** Organization administration is tenant-bound lifecycle/group/audit management, separate from installation operator access and resource authority. ADR-0040 owns grants/bootstrap/recovery and temporary global username/group/external-ID uniqueness. Tenant-scoped naming requires login/issuer/client/collision and restore design, not just a unique-index change. No customer-specific roles, automatic all-members content grant or mutable group as administrator authority is introduced.

## Schema, API, migration and rollback

Group checks and Files evaluator consolidation use existing columns; no schema migration is required by this ADR. Administrator grants and audit schema belong to ADR-0040; historical data mapping belongs exclusively to ADR-0043; database isolation belongs to ADR-0042. Effective-permission explanations are additive response fields, restricted to the principal and authorized resource grant managers. Roster field minimization is a proposed client-visible change: recommend co-member username/display name, email only to authorized tenant administration. Maintainer/security owner must approve that contract change before implementation; current #365 tenant scoping is not proof this minimization shipped.

Inventory mixed legacy deployments before deploying further strict checks or evaluator consolidation; report aggregate affected counts, preserve rows and open a quarantine/support ledger. #365 is already merged: the gate concerns rollout/remaining changes, not retroactive permission to merge. Restore/rehearse before approved mapping; never infer tenant from names, groups or email domains. If strict authorization rejects formerly reachable legacy data, keep denial and preserved data while operators review mapping. Rollback must not restore cross-tenant access or Edit publication. Prefer roll-forward or restricted service recovery over reverting security checks.

## Operations and performance

Reuse existing resource services and repositories; no distributed policy service, per-object membership reindex or new cache is required. Live group lookup and source checks add database work but preserve revocation correctness. Reuse the decision for explanations; instrument latency, query count, denied candidates and refresh failures without private content. Acceptance workload includes concurrent autosave/search, group changes and bulk operations at approximately 100 users; record p95/p99 authorization latency, pool wait and discoverability lag against a declared operator-approved budget. Do not infer capacity from user count. Support runbooks must distinguish delayed search inclusion from access denial, and provide bounded refresh retry and legacy quarantine handling.

## Required tests and acceptance

Extend `backend/tests/admin_groups_test.rs`, `backend/tests/group_sharing_test.rs`, `backend/tests/contracts/tenant_isolation_contract.rs`, `backend/tests/contracts/search_authorization_contract.rs`, `backend/tests/pilot_group_scope_inventory_test.rs` and `backend/server/tests/share_acl_propagation.rs` as applicable. Requirements below are not claims of new execution:

1. Same-tenant nil and non-nil group creation/membership succeed; absent or mismatched tenant writes nothing. Seeded legacy mismatch is preserved but does not resolve or leak roster data.
2. Resource owner outside recipient group succeeds; unauthorized group member cannot share; resource Admin outside recipient group succeeds; missing/foreign group and foreign resource deny without disclosure.
3. Overlapping grants choose highest valid permission; removing one path preserves others, final-path removal and group deletion deny subsequent API/search/source checks without content deletion.
4. Files HTTP and ResourceRef source authorization agree for synthetic resource/share/requester mismatches, including non-nil requester to nil resource and reverse direction.
5. Owner/Admin publication and explicit unpublication succeed; View/Edit deny without sidecar/public-index/search mutation. Test the documented sidecar availability residual separately and require its owner disposition.
6. Stale candidate ACL and missing minimum-version floors never bypass source checks before Memory or Agent materialization. Disabled/revoked actors cannot mutate memberships; ADR-0040 credential residual gates still apply.
7. Admin, SCIM, deletion and bulk refresh paths reach affected resources, including historical C4 fixtures; projection failure cannot widen access. Retry restores discoverability within the accepted budget.
8. Explanations match actual decisions and reveal no foreign/private grants; tenant administrator cannot implicitly read private resources or another tenant's audit.

Acceptance requires revision/image/deployment-bound gate artifacts, no unresolved security regression, reviewed inventory for affected rollout, tested operator procedures and measured workload results. See the [roadmap traceability matrix](../plans/2026-10-13-phase4-0-institutional-implementation-roadmap.md) and [institutional gates](../pilot/2026-10-13-institutional-acceptance-gates.md). Neither green CI nor these Proposed decisions constitute architecture approval. Object GC and orphan reconciliation remain disabled.
