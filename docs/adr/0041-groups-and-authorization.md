# ADR-0041: Groups and Organization Authorization

Status: Proposed — decision gate for Phase 4.0 (Institutional Authorization Decision Gate). This document authorizes no implementation.
Date: 2026-10-13
Baseline: commit `1ec2ea7a887ee0ab79d7d8ce525a0e5a76e0109e`

## Context

Evidence: the five Phase 4.0 source audits, the **executed** negative-test run report (`docs/audits/2026-10-13-phase4-0-tenant-isolation-negative-tests.md`) and the consolidated evidence matrix (`docs/audits/2026-10-13-phase4-0-tenant-isolation-evidence-matrix.md`), plus direct re-verification of every line cited below. Matrix row IDs (`P4-*`) and harness case letters are cited per claim; where a source audit and the executed evidence disagree, the executed evidence wins.

**Group identity exists but is not organization-bound.** `user_groups` was created with `name TEXT UNIQUE` — globally unique — and no tenant key (`backend/migrations/20260322000002_create_user_groups.sql`); `tenant_id` was added later as `NOT NULL DEFAULT '00000000-…'` (`20260329170001_add_tenant_id_to_tables.sql:28`), so "nil tenant" is a zero UUID, never NULL. `group_members` (`20260322000003_create_user_group_members.sql`) has `UNIQUE(group_id, user_id)`, membership rows cascade on group/user delete, and **no tenant column**.

**All three creation paths omit the tenant.** Admin panel `INSERT INTO user_groups (id, name, description, created_by)` (`backend/server/src/handlers/admin/groups.rs:183-185`), SCIM v1 (`handlers/scim.rs:490`), SCIM v2 (`handlers/scim_v2.rs:492-506`) — all take the nil default. Regular users cannot create groups: the user-facing surface is `GET /api/v1/groups/my[/{id}]` plus share management (`routes.rs:1349-1350`).

**Membership add/remove never validates the organization.** `add_member` reads the group's `tenant_id` (with a guard at `admin/groups.rs:454-456` that can never fire, because the column is `NOT NULL`, so `Some(nil)` always passes), verifies only that the *user* exists (`:459-469`), inserts the membership (`:472-484`), then spawns a best-effort index refresh (`:502-508`). `remove_member` mirrors it (`:523-572`, refresh at `:563-569`). SCIM v1/v2 group membership mutations (`handlers/scim.rs:557-575` add, `:577-591` remove, `:593-596` clear-all; `handlers/scim_v2.rs:632,647,669`) perform no organization check and trigger **no** index refresh. Executed, live: `POST /api/v1/admin/groups` returned `201` and stored a **nil-tenant** group; `POST /api/v1/admin/groups/{id}/members` for a tenant-B user returned `204` and stored a row with `member_tenant = B`, `group_tenant = nil`, `tenant_mismatch = t`; content stayed contained downstream (file request `403`, file list `200 []`), which is the share-tenant and user-tenant filters working, not a membership check (negative-test report §4(b); matrix `P4-08`, `P4-09`).

**Read paths ignore the group's organization.** `get_user_group_ids` joins `group_members` to `users` and filters on **the member's** tenant (`tenant_id = $2`), never joining `user_groups` (`backend/crates/infrastructure/src/repositories/permission_resolver.rs:160-175`). `GET /api/v1/groups/my/{id}` validates membership only and then returns every member's `username` and `email` with no tenant filter (`handlers/groups.rs:180-236`); `list_my_groups` likewise leaks names/descriptions cross-organization (`:124-164`). This is groups-workspaces audit **F1, a confirmed cross-tenant PII disclosure** (matrix `P4-15`), and **F2** (group `tenant_id` is decorative in every read path, matrix `P4-16`). Both are source-derived: the live run performed a roster read but the report records no cross-tenant leak assertion for it, and the matrix names this exact assertion (`GET /api/v1/groups/my/{id}` must not return other tenants' members) as an open follow-up (negative-test report §1.3 and §6 limits; matrix gap G2), so the roster test below is new coverage rather than a regression.

**Group-share creation validates the resource, never the group.** `create_group_share` checks `resource_tenant != tenant_id` (the audit's only explicit tenant check, `backend/crates/core/src/services/share_service.rs:953-956`) and then never loads the group; the doc comment at `:919` claims `CrossTenantSharingNotAllowed` fires "if group is in different tenant", which is false. `GroupNotFound` is mapped in the handler but never returned. Owners skip the membership check entirely (`:958-993`), and `is_user_in_group` has no tenant filter (`backend/crates/storage/src/metadata.rs:5559-5574`). Public-link creation checks ownership but not resource tenant (`share_service.rs:289-363, 367-451`). Resources-sharing audit findings 4, 5, 8 (matrix `P4-25`, `P4-26`, `P4-28`). Executed, live: an owner who was **not yet a member** of the recipient group created a group share with `201`, confirming the skipped `is_member` branch — the handler maps `GroupNotFound` / `NotGroupMember` errors that the owner path can never produce (negative-test report §4(g)).

**Resolution semantics today.** `check_file_permission` / `check_folder_permission` resolve owner → direct share → group shares (highest permission wins) → folder ancestry (`backend/crates/core/src/services/permission_resolver.rs:193-304, 315-425`); every share lookup is filtered by `shares.tenant_id = <lookup tenant>` (`share_repository.rs:41-45`). Group membership is expanded live per request with the per-request cache cleared at each top-level check (`:200-202`). A cross-org group is therefore inert for content today — a content bypass is not reachable — because the *share's* tenant check happens to compensate. That is an unenforced invariant, not a defense (audit F2; matrix `P4-16` for the unenforced group tenant, and `P4-30` for the executed consistent-data resolution: a same-tenant member resolves the group share while a cross-tenant requester and a non-member resolve nothing).

**Effective-access explanation is computed and discarded.** `PermissionSource` (`Owner|DirectShare|GroupShare|Inherited|None`, `permission_resolver.rs:26-49`) and `resolve_permission_with_source` (`:796-812`) exist and are called (`handlers/user_shares.rs:570,612,649,724`), but responses keep only the permission level (`:638,:678,:685`). No API explains why a user has access (audit F6, ADR-0038 decision 6 unimplemented; matrix `P4-20`).

**Revocation and the materialized AI-index ACL.** Content access revokes immediately (live joins). Search retrieves live group IDs at query time (`backend/crates/core/src/services/ai_service.rs:175-197`) and re-authorizes every candidate twice (`ai_service.rs:300-319`, `unified_search.rs:366-380`), so a stale index cannot grant a result (see `0036-unified-search-permission-model.md`; contract `:99,126`). But `refresh_index_acl_for_group` filters shares with `tenant_id = $2` using the **group's** tenant (`backend/server/src/services/note_service.rs:899-905`), which for every admin/SCIM-created (nil-tenant) group matches no share row — a guaranteed silent no-op on every member add/remove (**defect C4**). Executed: against rows created by ordinary authenticated calls (live `POST /api/v1/admin/groups` → nil-tenant group, then `POST /api/v1/files/{id}/share/group` → `201` with the caller's real tenant) the shipped filter returns 0 while the corrected filter returns 1, so the triggering state is **DIRECT-API-producible, not synthetic** (negative-test report §4(g); matrix `P4-31`, `#287-R19`). `delete_group` cascades share rows (`recipient_group_id … ON DELETE CASCADE`, `20260401000001_add_group_sharing.sql:6`) but spawns no refresh (`admin/groups.rs:389-425`). Refresh is fire-and-forget (`tokio::spawn`, errors logged only) with no redrive. The `min_acl_versions` stale-version rejection (`vector_store.rs:132-136`) is never armed in production (`ai_service.rs:196,265`) — contract rules 4/5 advertise a backstop that is inert (audit findings 1, 3, 4, 5).

**Two evaluators, different scoping.** `PermissionResolver` is tenant-scoped; `check_resource_permission` (`share_service.rs:1240-1345`) uses unscoped `get_file_shares`/`get_folder_shares`/`is_user_in_group` (`metadata.rs:5194-5225, 5559-5574`) and gates share management (resources-sharing finding 8). The Files service keys the resolver off the *resource's* tenant (`file_service.rs:865,872`) while the source authorizer of `0032-resource-refs-and-authorization.md` keys off the *requester's* tenant (`authz/files_owner.rs:237-246`) — the C3 asymmetry, synthetic-only today, with the notes layer closing it via an explicit post-check (`note_service.rs:1361-1363`). Executed: the two keyings return opposite decisions for the same database state (matrix `P4-22` — the file-tenant lookup grants View, the requester-tenant lookup denies), the second evaluator is unscoped (`P4-28`), and the mismatched row itself is **SYNTHETIC**: no share-creation path produces it (negative-test report §4(f)).

**Test coverage gap.** `backend/tests/group_sharing_test.rs`, `backend/tests/admin_groups_test.rs`, `backend/tests/pilot_group_scope_inventory_test.rs` and `backend/tests/contracts/search_authorization_contract.rs` exist, but none asserts organization match on membership or group-share creation (audit testing note).

**Product requirements.** #330 requires bounded organization roles, group membership with deterministic access effects, rejected cross-tenant membership, and understandable effective membership; #331 requires tenant-scoped bulk onboarding/offboarding with idempotency; #333 requires permission-negative tests at Gate C and forbids customer-specific role models.

## Decision

**D1. A group belongs to exactly one organization; `user_groups.tenant_id` is authoritative.** No global, cross-organization, or "all members" group exists in Phase 4.0, and no request may create one. All three creation paths (`admin/groups.rs:183-185`, `scim.rs:490`, `scim_v2.rs:492-506`) must write `tenant_id` from the creating principal's resolved organization, which requires no schema change because the column exists. `group_members` gains **no** tenant column: membership organization is derivable from the group, a second copy can drift, and write-time equality validation (D2) is the control. `external_id` for groups stays globally unique (ADR-0040 D6).

A nil-tenant group means a group of the **default organization** (ADR-0040 D4). Where the deployment's default organization is non-nil, nil-tenant groups are legacy rows that grant nothing (D3) until an operator-approved mapping exists (ADR-0043).

Group names remain **installation-globally unique** in Phase 4.0 (`user_groups_name_key`): a second organization in the same installation would have to choose globally unique names, and the operator runbook must say so. Moving to `UNIQUE(tenant_id, name)` is lossless (global uniqueness implies composite uniqueness) and belongs to ADR-0043's migration slice rather than this gate.

**D2. Every membership and every grant validates organization equality at creation.** Binding rules, to be applied on every path:
- `add_member` (admin and SCIM): load the group, require `users.tenant_id == user_groups.tenant_id`; on mismatch return a client error and write nothing. The unreachable "Group missing tenant_id" guard (`admin/groups.rs:454-456`) is removed rather than relied upon. Executed: the current code accepts the cross-organization row (live `204`, stored `tenant_mismatch = t`; negative-test report §4(b); matrix `P4-09`), so this rule changes observed behavior, not a hypothetical one.
- SCIM group membership: resolve member references inside the SCIM token's organization (ADR-0040 D5) and reject members from another organization.
- `create_group_share`: load the group (`GroupNotFound` becomes reachable), then require `group.tenant_id == resource.tenant_id == requester organization`. The doc comment at `share_service.rs:919` must either become true or be deleted; leaving a false security claim in place is not acceptable. The owner path's skipped membership check is confirmed live (negative-test report §4(g); matrix `P4-25`): an owner who is not a member of the recipient group must be validated by the same rule, not exempted from it.
- Public-link creation (`share_service.rs:289-363, 367-451`): add the missing `resource.tenant_id == requester organization` check.
- Bulk membership operations (#331): validate every row before mutating, be idempotent, and emit **one** index-refresh pass per affected group rather than per member.
- Removal paths validate the same equality as the add path, so a mismatched legacy row cannot be "repaired" into a privilege.
- No nested groups in Phase 4.0. If group-in-group is ever added, it must be cycle-checked and organization-checked; until then "group-derived access" means "access via a share granted to a group the principal is a direct member of".

**D3. Every group read path is organization-scoped.** Three changes, all code-only:
- `get_user_group_ids` must additionally join `user_groups` and require the group's organization to equal the requester's (`... JOIN user_groups g ON g.id = gm.group_id WHERE gm.user_id = $1 AND g.tenant_id = $2`) — `backend/crates/infrastructure/src/repositories/permission_resolver.rs:160-175`. This one predicate closes F1's group-expansion channel and makes group `tenant_id` operative in resolution. Executed for the underlying defect: the cross-tenant membership row is storable through the admin API and never resolves for the member (`get_user_group_ids` returns `{}`), which is exactly why the read predicate — not the missing write check — is the only thing enforcing the boundary today (negative-test report §4(b), probes 6–9; matrix `P4-09`, `P4-16`).
- `get_my_group` and `list_my_groups` (`handlers/groups.rs:124-164, 180-236`) must filter group and member rows by the requester's organization, so a group roster can never contain a principal from another organization.
- The roster response becomes a deliberate product decision: members may see co-members' `username` and display name within their organization; member `email` is exposed only to organization administrators. Recommendation and rationale are in the approval list, because this narrows an existing response and affects clients.

**Compatibility consequence, stated explicitly.** D3's resolver predicate is a behavior change, not only a hardening: in a deployment where an operator set a non-nil default organization and groups were created nil by the admin UI or SCIM, current members lose the group-derived access those mismatched groups were granting. This is the intended fail-closed direction (nothing is granted by accident), it is a **revocation**, and it therefore requires the inventory run and human approval before it lands. Rollout order: (1) write-path validation (D2) and read-path roster scoping — no access revocation; (2) run `scripts/pilot-group-scope-inventory.sql` and review the mismatch classes; (3) land the resolver predicate (one line, individually revertible); (4) collapse the second evaluator by delegating `check_resource_permission` to `PermissionResolver` (D4) — the prerequisite for calling resource-level permissions authoritative, and the slice that carries the publish fix; (5) remediate mismatched groups through ADR-0043's operator-approved mapping. No step deletes membership rows, infers an organization, or auto-repairs data.

**D4. One authorization engine; resource-level permissions stay authoritative (ADR-0032).** No second permission engine, no group-specific ACL table, and no materialized file/folder permission table is introduced. Group-derived access is expressed only as share rows with `recipient_group_id`, resolved exclusively by `PermissionResolver` with these binding rules:
- The **share row's organization is the operative filter** and must equal the resource's organization and the requester's organization. Resolution may not depend on the requester's tenant alone compensating for a mismatched share.
- The invariant `resource.tenant_id == principal.tenant_id` is checked at the service boundary (the notes pattern, `note_service.rs:1361-1363`) so the Files HTTP surface and the ADR-0032 source authorizer cannot disagree — the C3 asymmetry is resolved in favor of the requester tenant plus an explicit resource-equality check, before resource-level permissions can be called authoritative.
- `check_resource_permission` (`share_service.rs:1240-1345`) stops being a second evaluator: it **delegates to `PermissionResolver`** for every decision. Delegation, not parallel re-implementation, is the only option consistent with "no second permission engine" — re-implementing the same organization-scoped rules a second time would reproduce exactly the divergence that exists today (matrix `P4-28`; resources-sharing finding 8), and the unscoped `is_user_in_group` / `get_*_shares` calls it currently uses must stop gating share management. This is step (4) of the rollout order above, and it is a prerequisite for calling resource-level permissions authoritative.
- Organization membership, group membership, and any future workspace membership grant **no** content access by themselves. Because workspace is the organization in Phase 4.0 (ADR-0040 D2), the only paths to file or note content remain ownership, direct shares, group shares, and folder ancestry — highest permission wins, additive, exactly as today. This is what gives #330's "deterministic effects of group membership" a precise meaning: the effect is on the set of share rows that resolve for a principal, nothing more.
- Adjacent confirmed defect in the same decision area: a recipient holding only **View** on a note can currently publish it (`toggle_visibility` requires View only, then sets `visibility=Public` and writes a public index, `note_service.rs:2667-2701`; served unauthenticated at `:2729-2765`) — resources-sharing finding 3, a confirmed access bypass. Publishing is not reading: making a resource public must require ownership, `Edit`, or `Admin`. Recommended to be fixed with this ADR's slice and covered by the permission-negative tests.

**D5. Bounded roles; organization administration is metadata-only.** Role vocabulary is closed for Phase 4.0: `member` (implicit in `users.tenant_id`) and `administrator` (explicit grant per ADR-0040 D7), plus the unchanged resource capabilities `View|Edit|Admin|upload_only`. No school, class, student, subject, or customer-specific role, group type, or hierarchy exists. Organization administrators may create, rename and archive groups, and add/remove members of their organization only; they may not manage other organizations, and they may not read, search, or enumerate share grants on resources they neither own nor hold a share for. The hard constraint is enforced structurally: there is no administrative path into the content resolver (verified — no admin handler reads file or note bodies), and the invariant plus negative test keep it that way.

**D6. Family explanation of effective access (ADR-0038 decision 6).** `PermissionSource` must reach the client: the existing share/permission responses gain an additive `effective_permission_source` (and, where available, the granting `share_id` and the group or ancestor folder that produced it), sourced from the same `resolve_permission_with_source` call that made the decision — never from a second evaluation. Explanations are display and audit aids; clients must not use them for authorization. For #330's "why does this user have access to this workspace", with workspace = organization the honest answer is organization membership plus the organization role; resource-level grant paths are reported only to the principal itself and to owners/resource admin, never to organization administrators on resources they do not control. Cost is an additive response field; no new endpoint, no new authority.

**D7. Membership revocation semantics are preserved and made complete.**
- Content access: immediate. Live `group_members` joins with the per-request cache cleared at every top-level check (`permission_resolver.rs:200-202`); a removed member loses access on the next request. Preserve and test.
- Search: fail-closed and effectively immediate. Retrieval expands the requester's groups live (`ai_service.rs:175-197`) and re-authorizes every candidate against the owning source (`ai_service.rs:300-319`, `unified_search.rs:366-380`), so a stale materialized `group:{id}` principal can produce a candidate but never a result. The materialized ACL remains a coarse candidate filter only (ADR-0036), and group membership changes continue to require no per-object reindex (contract `:99,126`).
- Group deletion: cascades membership and share rows, so derived access ends immediately, but must now trigger the same best-effort ACL refresh as add/remove, otherwise stale `group:{id}` principals are left in the index (`admin/groups.rs:389-425` spawns nothing today). Group deletion must never delete or orphan resource content.
- Non-durable, best-effort refresh with no redrive is **accepted** for Phase 4.0; adding an outbox, queue, or reconciliation worker is explicitly out of scope, because the live re-authorization is the guarantee and the refresh is a recovery/optimization path (audit §4).

**D8. Group-driven AI-index ACL refresh: adopt the smallest safe correction.** `refresh_index_acl_for_group` (`note_service.rs:897-946`) must filter by `recipient_group_id = $1 AND revoked_at IS NULL` **only**, selecting each share row's own `tenant_id`, and pass **that** tenant to the per-resource refresh: `SELECT file_id, folder_id, created_by, tenant_id FROM shares WHERE recipient_group_id = $1 AND revoked_at IS NULL`, then `refresh_index_acl_for_resource(resource, created_by, share_tenant)`. Per-resource tenant scoping is preserved by `refresh_note_index_acl`, which continues to require `file.tenant_id == tenant` (`note_service.rs:810-812`). This fixes the C4 no-op for nil-tenant groups with one function change and no new infrastructure. Additionally: group deletion and SCIM membership mutations (admin UI refreshes; SCIM does not — `handlers/scim.rs:557-575,577-591,593-596`, `handlers/scim_v2.rs:632,647,669`) are brought to parity through a single internal helper, so every membership mutation path behaves identically — the audit flags the SCIM v2 membership path as read-verified but not runtime-verified, so parity plus a test, not documentation alone, is required. Required test: an integration case with an **admin-created (nil-tenant) group** whose note was shared by a real-tenant user, asserting the membership-change refresh actually reaches the resource (`backend/server/tests/share_acl_propagation.rs` is the existing home; the audit notes no nil-tenant case exists there). Executed: this triggering state is **DIRECT-API-producible, not synthetic** — ordinary calls (`POST /api/v1/admin/groups` then `POST /api/v1/files/{id}/share/group` → `201`) create the nil-tenant group and the real-organization share row, and against those rows the shipped filter returns 0 while the corrected filter returns 1 (negative-test report §4(g); matrix `P4-31`, `#287-R19`).

**D9. `min_acl_versions` is not armed in production; the contract language is softened instead.** Decision: keep the live per-result re-authorization as the single stale-ACL backstop (ADR-0036) and amend `docs/contracts/permission-aware-indexing-contract.md` rules 4/5 to state that version comparison is a fail-closed *backstop for callers that supply* minimum versions, and that production retrieval currently supplies none, relying on live re-authorization. Rationale: arming it requires the current source `acl_version` per candidate before the search — a metadata read per candidate that duplicates the re-authorization already performed, and a new fail-closed dependency whose version semantics could suppress legitimately visible results. The audit identifies no security benefit from arming it. The contract edit is a documentation change to an Accepted contract and therefore needs sign-off (approval item 4); this ADR does not perform it.

**D10. Nothing here activates garbage collection or orphan reconciliation.** No decision in this ADR enables, implies, or depends on production GC or orphan reconciliation (ADR-0040 D9). Object GC and Phase 3.4B orphan reconciliation remain disabled by default and out of scope.

## Relationship to ADR-0038 (decision by decision)

- **Decision 1 (tenant = boundary): extended.** Realized for groups as D1–D3: the group's organization becomes operative in creation, resolution and read paths, closing the metadata-plane violations F1/F2 without a data rewrite.
- **Decision 2 (workspace distinct, tenant-bound): refined and deferred.** ADR-0040 D2 makes workspace = organization in Phase 4.0, so the binding "membership must be tenant-bound" becomes D2's creation-time equality rules and D3's read-path scoping. Workspace membership remains unimplemented; no workspace role or group→workspace mapping is introduced here.
- **Decision 3 (installation vs organization admin): extended.** D5 implements the "no implicit access to private resources" clause as a structural property with a negative test, and bounds the organization-administrator group capability set. Role storage and life cycle are ADR-0040 D7.
- **Decision 4 (legacy groups, no in-place broadening): affirmed; partially refined.** This ADR adds **no** in-place rewrite of legacy ACL groups; it does change *resolution* for organization-mismatched groups (D3), which is a fail-closed semantic change requiring the inventory and approval, and leaves all remediation (mapping, backfill) to ADR-0043. "Group membership and workspace membership remain distinct concepts" is preserved.
- **Decision 5 (membership is not a universal content grant): implemented.** D4 states that group and organization membership grant no content access by themselves, and that only ownership and explicit shares resolve.
- **Decision 6 (additive, explainable, immediately revocable): implemented and refined.** D6 surfaces `PermissionSource` additively; D7 preserves immediate content revocation and fail-closed search behavior, and records where the index projection is only eventually consistent. The audit's finding that `PermissionSource` is computed and discarded is fixed by D6.
- **Decision 7 (Calendar unchanged): affirmed.** Calendar has no sharing mechanism and no AI index, so nothing here applies to it (resources-sharing finding 10; search-index audit §1 note).
- **Existing-data and migration constraints: affirmed.** No inference of an organization for nil-tenant groups, shares, resources or audit rows from a zero UUID or a name; new constraints and tables are additive first and must fail on unresolved references rather than dropping or granting access. This ADR's D3 resolution change is precisely the kind of enforcement ADR-0038 gates on an inventory result, which is why the inventory precedes it in the rollout order.
- **Approval required: affirmed.** ADR-0038's approval requirement carries over: nothing in D2–D8 proceeds without the human approvals listed below, and the changes with security-side effects — D3's resolver predicate, D4's evaluator collapse, the publish fix, and D8's refresh parity — need the security-owner sign-off that ADR-0038 demands for authorization changes.
- ADR-0038 remains **Proposed and in force**; it is extended, refined and implemented by this ADR, not superseded.

## Schema impact, migration cost and rollback

- **No schema migration required:** D1 (write the existing `tenant_id` column on group creation), D2 (creation-time equality validation), D3 (read-path predicates), D4 (resolver keying and evaluator unification), D5 (roles unchanged; groups are metadata-only for administration), D6 (additive response field), D7/D8 (refresh plumbing), D9 (documentation).
- **Schema changes implied elsewhere, not by this ADR:** the lossless `UNIQUE(tenant_id, name)` change (D1) and legacy nil-tenant group remediation (ADR-0043); organization-administrator grants and `admin_actions.tenant_id` (ADR-0040 D7, #332).
- **Cost:** primarily test and client-response surface (D6) plus one function change (D8). D3 is one predicate in `get_user_group_ids` and two scoped queries in the user-facing group handlers.
- **Rollback:** every item is individually revertible. D2/D3 must be rolled forward through the inventory because reverting the resolver predicate restores currently mismatched access; that is the only change whose rollback is a security regression, and it is exactly why approval and inventory precede it.

## Security invariants

- **B1 — Group organization integrity.** Every group and every membership row belongs to exactly one organization. No path creates or preserves a membership whose principal and group organizations differ.
- **B2 — Grant equality.** At creation and at resolution, the share row's organization, the resource's organization, and the grantee's organization (user or group) are equal. No path grants cross-organization access, including by omitting a check.
- **B3 — Single engine.** No authorization decision for file/note content is made outside `PermissionResolver` and the owning application's source authorizer (ADR-0032). No group-specific ACL cache, second evaluator, or materialized permission table exists.
- **B4 — Administration is metadata-only and non-disclosing.** Organization administration never reads content and never enumerates grant paths on resources the administrator does not own or hold a share for.
- **B5 — Immediate revocation, candidate-only index.** Removing a membership revokes content access on the next request regardless of index state; the index is a candidate filter that can never produce an unauthorized result.
- **B6 — Group deletion is capability-revoking and content-safe.** Deleting a group ends all derived access immediately, leaves no stale index principal that could match, and never deletes or orphans resource content.
- **B7 — Fail closed on ambiguity.** Missing organization, unknown group, or mismatched organization yields deny (404/403). No path substitutes the default organization, a name, or an email-derived guess.
- **B8 — Additive, explainable grants.** Removing one grant path removes only that path; explanations come from the same resolution that decided, and are never an authorization input for clients.

## Negative tests required by this ADR

Extend `backend/tests/admin_groups_test.rs`, `backend/tests/group_sharing_test.rs`, `backend/tests/contracts/tenant_isolation_contract.rs`, `backend/tests/contracts/search_authorization_contract.rs`, `backend/tests/pilot_group_scope_inventory_test.rs`, `backend/server/tests/share_acl_propagation.rs`.

1. **Same-organization membership allowed.** Adding a same-organization user to a same-organization group succeeds and group-derived access resolves.
2. **Cross-organization membership rejected.** Admin API and SCIM add attempts across organizations are refused and no row is written; removal paths reject the same way.
3. **Group share resolution is scoped.** A share created for a group yields access only to members of the same organization; a mismatched (or nil-with-non-nil) group grants nothing after D3.
4. **Group-share creation validation.** Sharing with a nonexistent group returns `GroupNotFound` (currently unreachable); sharing with a group from another organization is refused; resource/requester organization mismatch is refused; public-link creation refuses a resource of another organization.
5. **Membership removal invalidates access.** Removed members lose direct API access on the next request and disappear from search results; removing one path leaves other valid paths intact (additive grants).
6. **Legacy nil-tenant group behavior, in the corrected direction.** Within a default (nil) organization, a nil user in a nil group with a nil share still resolves (executed probe 15). A non-nil user gains nothing through a nil group (executed probes 8–9), and a nil group must not become a route into real-organization content. The previously reported chain in the other direction — a nil principal reaching a real-tenant file — is **refuted** and must not be encoded as a test (executed probes 13–14); the live variant is a real-organization principal reaching **nil**-tenant resources through nil-tenant share rows (probe 16), which must be asserted as denied once D2/D3 land. (negative-test report case (e); matrix `P4-14`, `#287-R17`.)
7. **Cross-tenant resource/share mismatch.** A seeded mismatched share/resource/recipient state fails closed, and the Files surface and the source authorizer return the same decision (the C3 probe).
8. **Admin-created group AI-index refresh.** With an admin-created (nil-tenant) group whose note was shared by a real-organization user, a member add/remove triggers a refresh that actually reaches the resource, and group deletion clears the stale `group:{id}` principal.
9. **Roster non-disclosure.** `GET /api/v1/groups/my/{id}` and `list_my_groups` never return principals, names, or descriptions from another organization.
10. **Org admin cannot implicitly access private content.** An organization administrator receives no content from a private file or note owned by another member (or another organization), neither through the API nor through unified search, and cannot enumerate its share grants.
11. **Publish is not read.** A recipient with only `View` cannot make a note public (D4, resources-sharing finding 3); ownership and `Edit`/`Admin` can.
12. **Disabled actor and revoked credentials (re-anchored).** The previous anchor was the refuted F4 claim; the property is now anchored on the database trigger and executed evidence: disabling any principal must leave `user_sessions` empty and `device_tokens.revoked_at` set for every writer, including the SCIM-shaped update (executed baseline: negative-test report case (h); matrix `P4-10`; regression-asserted in `backend/tests/user_disable_credential_revocation_test.rs`), with the residual stateless-JWT exception asserted explicitly rather than implied (ADR-0040 D8, approval item 9). Membership mutations performed by a disabled or revoked actor are refused.

## Alternatives considered

- **Add a tenant column to `group_members` and validate both sides.** Rejected: membership organization is derived from the group, a second copy can drift, and the enforcement point is the write path (D2) plus the read predicate (D3). This also avoids a backfill with no authoritative source.
- **Leave resolution as-is and fix only the roster leak.** Rejected: it fixes the PII symptom (F1) but leaves the group-tenant invariant unenforced (F2), which becomes a live bypass the moment any resolver path stops tenant-filtering shares. The audit classifies it as an unenforced invariant, not a defense.
- **Only validate at creation, never change resolution (avoid all revocation).** Rejected as the end state: it leaves existing mismatched groups granting access through the same unenforced invariant. Sequencing (D3) is the concession: validation and roster scoping land first, the resolution predicate lands after the inventory is reviewed and approved.
- **Reuse an ACL group for organization administration.** Rejected in ADR-0040 D7: mutable, globally named, user-visible container as a privilege source.
- **Introduce a group-level permission table or materialized ACL for files/folders.** Rejected: it is a second authorization engine, contradicts ADR-0032/0036 ("index/permission caches are never authorization"), and reintroduces the revocation-staleness problem the live joins avoid.
- **Nested groups (group-in-group).** Rejected for Phase 4.0: it multiplies resolution cost and introduces cycle and organization-mixing failure modes for no requirement in #330/#331.
- **Arm `min_acl_versions` in production.** Rejected (D9): cost without security benefit, and it adds a fail-closed dependency that can suppress legitimate results.
- **Make the index refresh durable (outbox/queue) now.** Rejected for Phase 4.0: no security benefit while re-authorization is live, and it adds operational surface the milestone does not require. Refresh-loss consequences are documented instead.
- **Make group names organization-unique immediately.** Deferred (D1): the change is lossless but belongs with ADR-0043's migration slice rather than this no-migration gate.

## Consequences

- The metadata-plane cross-organization disclosures (F1, F2) are closed by construction; group `tenant_id` becomes operative rather than decorative.
- Organization-mismatched and nil-tenant group populations change behavior: strict equality can revoke access that is currently (accidentally) working. This is a pre-approved-inventory, human-approved revocation, not a silent one. The risk direction is stated in the corrected form after the executed evidence: within-nil resolution (which a default deployment manufactures through the API) and real-organization principals reaching **nil**-tenant resources via nil-tenant share rows — not, as previously asserted, a nil principal reaching a real-tenant file (negative-test report case (e) and §5.1; matrix `#287-R17`).
- Group membership's "deterministic effect" on permissions is now precisely defined: it changes which share rows resolve, and nothing else. Product expectations that a group implies content access must be corrected in the UI copy and in #330's acceptance criteria.
- The effective-access explanation is additive and cheap but incomplete for nested/hierarchical grant paths (folder ancestry is reported at the nearest ancestor, not as a full chain).
- Organization administrators remain deliberately weak: metadata administration only, no content, no grant enumeration. This can be read as under-delivering on #330's "understand the effective workspace role" for resources; with workspace = organization, the answer is org membership plus role, and per-resource grant introspection stays with resource owners.
- Search visibility for newly added members can lag until the best-effort refresh runs, and refresh loss has no redrive. Access is unaffected because retrieval re-authorizes live; this must be documented rather than silently accepted, and the contract wording is corrected per D9.

Recommended: approve after reviewing `scripts/pilot-group-scope-inventory.sql` output; it is the only way to make the group-tenant invariant enforced rather than decorative.
2. **Decide the group roster content**: recommendation is username and display name visible to co-members within the organization, member emails visible only to organization administrators. This narrows an existing response and affects clients.
3. **Confirm that group/organization membership confers no content access in Phase 4.0** (D4) and that #330's "deterministic effects on permissions" is satisfied by explicit share resolution. Recommended: confirm, and update the issue's acceptance wording so the product expectation matches the security model.
4. **Approve the `permission-aware-indexing-contract.md` wording change for `min_acl_versions` (D9)** and the `workspace_id` wording in ADR-0040 D2; both are documentation edits to an Accepted security contract.
5. **Decide whether the resources-sharing finding 3 fix (publishing requires ownership, `Edit`, or `Admin`) ships with this slice** or as a separate security fix. Recommended: ship with the resource-level permission work in this slice, since it is a confirmed in-tenant privilege escalation and the same tests cover it.
6. **Approve `UNIQUE(tenant_id, name)` for group names and its placement** (ADR-0043's migration slice vs a follow-up release). Recommended: ADR-0043's slice, keeping this gate migration-free; if a second organization must exist in Phase 4.0, move it here.
