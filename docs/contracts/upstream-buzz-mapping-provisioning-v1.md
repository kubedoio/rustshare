# Upstream Buzz Mapping Provisioning Contract v1

**Status:** Selected for an inert, feature-disabled implementation foundation. Independent security acceptance and production use remain gated.

## Authority

The trusted Elembra deployment/operator service is the only mapping writer. Human `AdminUser`, tenant `OrganizationAdmin`, users, Buzz relay identities, and unsigned NIP-11 metadata do not authorize mapping writes.

The operator service holds a dedicated Ed25519 signing key. The backend receives only the matching allowlisted public key(s), provisioned through trusted deployment configuration. The operator key is distinct from user identities, relay-owner/member-admin keys, identity-wrapping keys, and webhook credentials. A signed provisioning statement is the service authentication and authorization proof; an API caller cannot choose its own verification key or supply an unsigned mapping. The verifier is constructed from deployment-owned trust configuration, never request fields.

The signing service is trusted to attest facts it obtains from the deployment orchestrator and relay provisioning workflow: tenant/workspace assignment, stable relay deployment/service identity, exact community UUID, canonical endpoint, source/image digest, relay public key, and allowed network destinations. It must not derive the relay key or community from NIP-11 or ordinary client input. The signed statement is evidence of the trusted control plane's attestation, not independent proof that an arbitrary public endpoint belongs to the deployment. TLS, pinned DNS/peer checks, signed NIP-29 metadata where supported, and independent provenance acceptance remain required before production.

## Signed record

Every provisioning statement signs a versioned, domain-separated, deterministic binary encoding of:

- operator service UUID and operator signing-key ID;
- unique operation UUID, change-reference UUID, action, and expected generation;
- tenant UUID, workspace UUID, mapping UUID, and unique relay deployment UUID;
- immutable endpoint/service identity;
- canonical `wss://` URL (including port), exact DNS host, community UUID, pinned relay public key, source/image SHA-256 digest, and complete approved IP set;
- target generation, active state, mapping expiry, issued-at and short expiry.

The verifier enforces the configured operator identity and key ID, Ed25519 signature, short validity window, canonical UUID/community/URL representation, mapping policy, and action/generation relation. Create is generation 1 with expected generation 0. Update/renew/deactivate are compare-and-swap operations that increment the expected generation exactly once. Workspace binding is separately signed and references the current mapping and generation. A unique operation UUID is stored in append-only audit to reject replay; stale or duplicate updates fail closed.

The storage API accepts only a verified statement for create, bind, update, renewal, and deactivation. Request inputs cannot override relay address, community, identity, provenance, operator actor, or expected generation after signature verification. `updated_by` is the configured operator service UUID, and audit stores the signing key ID, operation UUID, and change reference.

## Data model and policy

One tenant owns exactly one relay deployment and community. Workspace records bind to that tenant mapping. `relay_deployment_id` and endpoint/service identity are globally unique so one deployment cannot serve two tenants. The community identifier is a canonical UUID generated by the trusted installer and bound to the dedicated relay; stock upstream Buzz has no HTTP community-discovery/creation contract, so Elembra must not claim the UUID was learned from the relay. Port is the exact canonical URL port and is part of the signed endpoint.

`strict_public` remains the only implemented endpoint policy. The mapping includes source/image digest, relay identity, approved addresses and generation. DNS answers are validated against the entire approved set and pinned to the actual socket; TLS hostname/SNI and peer are verified. NIP-11 `self` is only an unsigned consistency claim. No arbitrary client URL, DNS answer, proxy setting, redirect, host, service identity, or community may substitute for the signed statement.

Private/bundled `trusted_service` endpoints remain unrepresentable in this writer until their independent typed policy and network-enforced egress controls are separately accepted and proven.

## Private bundled relay qualification design

The transport profile must use a distinct type, for example `RelayEndpointPolicy::StrictPublic` and `RelayEndpointPolicy::TrustedService(TrustedServiceBinding)`. Do not add a private-address exception to `strict_public`. `TrustedServiceBinding` is constructed only from operator-signed provisioning state and contains an immutable orchestrator identity (cluster/project, namespace, service UID), exact canonical hostname and port, exact community UUID, pinned relay public key and artifact digest, TLS hostname and peer/SPKI identity, and approved service addresses. A caller cannot construct or select the private policy from a URL or API field.

The connector must resolve through the trusted deployment resolver, validate the returned addresses against the exact service binding, dial a pinned address directly, preserve the configured hostname for SNI and certificate verification, verify the connected peer and relay identity, and disable proxies and redirects. Tenant and generation remain part of the connection-pool key. A changed or expired mapping closes existing sockets and forces authorization revalidation. Cluster network policy or host firewall rules must independently deny egress beyond the exact approved service destinations; application checks alone do not qualify the exception.

Disposable qualification must run against an isolated Docker/Kubernetes service deployment with the same network enforcement intended for the deployment profile. It must prove the allowed service connects, while denied egress blocks loopback, metadata endpoints, unrelated private services, public destinations, alternate ports, redirects, proxy substitution, cross-tenant service reuse, DNS rebinding, stale generations, certificate/SNI mismatch, peer substitution, and relay-key/community mismatch. A loopback-only success without enforced egress is not evidence for production. Current qualification status: **UNVERIFIED**; no network-enforced bundled/private relay test has been accepted. Keep `trusted_service` unavailable until that test and independent review pass.

## Failure, audit and recovery

Invalid/revoked signer, signature, identity, provenance format, generation, operation replay, expiry, DNS, TLS, peer, tenant, workspace, or audit mismatch fails closed. Do not use the operator signing key to sign Chat events or relay membership. Do not log signatures, provisioning payload secrets, private signing keys, user keys, or message bodies. Audit records contain operator service identity, signer key ID, operation ID, change reference, generation and changed mapping fields.

Control-plane recovery requires restoring the trusted operator public-key allowlist and the signing service's separately protected private-key backup. Rotate by accepting an explicitly versioned new public key while retaining/revoking old key IDs through a reviewed process. A database backup alone is not mapping authority. No migration or restore may silently synthesize, rotate, or re-enroll mappings.

## Acceptance

Before any route or production caller is enabled, independently review signer key custody, trust-root rotation/revocation, deployment/orchestrator provenance, exact tenant/community isolation, audit and replay behavior, and operator recovery. Disposable tests must cover forged/unknown/revoked signatures, wrong tenant/workspace, client-supplied URL, source-digest substitution, duplicate deployment/service identity, stale generation, expired statement/mapping, replay, update/deactivate races, cross-tenant relay reuse, TLS/DNS substitution, and audit immutability. This contract does not authorize real-user key creation, signing, export, managed Chat routing, or release.
