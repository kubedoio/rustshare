## TODO-008: Fix global unique constraints for multi-tenant module/template keys

**Status:** OPEN

**What:**
Change database unique constraints from global `(module_key)` and `(template_key)` to tenant-scoped `(module_key, tenant_id)` and `(template_key, tenant_id)`.

**Why:**
The current migrations define `module_key VARCHAR(50) UNIQUE NOT NULL` and `template_key VARCHAR(100) UNIQUE NOT NULL`. The application code correctly queries by `tenant_id`, but the schema would reject the same predefined module or template for a second tenant.

**Severity:** Medium
**Area:** Backend Database Schema
**Evidence:** `backend/migrations/20260429220001_create_modules_table.sql`, `backend/migrations/20260429220002_create_templates_table.sql`

**Recommended fix:**
- Create new composite unique indexes: `UNIQUE(module_key, tenant_id)` and `UNIQUE(template_key, tenant_id)`
- Drop the old global unique constraints
- Verify `ensure_default_modules` and `ensure_default_templates` work correctly for multiple tenants

## TODO-011: Decouple NoteService from hardcoded "Notes" module key

`NoteService` is tightly coupled to the Notes module through hardcoded strings. This prevents reuse of the note-taking logic for other file-backed modules and creates a hidden dependency between the service and a specific module key.

**Evidence:** `backend/server/src/services/note_service.rs:189-271` contains hardcoded `meta/notes/`, `meta/notes/public/`, and folder name `"Notes"`.

**Recommended fix:**
- Add a `module_key` or `root_folder_name` parameter to note service methods
- Or inject module configuration into `NoteService` at construction time
- Update all callers (handlers, other services) to pass the correct module context

## TODO-012: Add backend icon validation against approved registry

**Status:** OPEN

**What:**
Validate the `icon` field in `UpdateModuleRequest` against the approved icon registry on the backend, not just the frontend dropdown.

**Why:**
Currently only the frontend validates icon selection. A malicious or buggy client could send an arbitrary icon string that the backend would persist. While this is low-risk (icons are rendered through a lookup component), it violates the defense-in-depth principle.

**Severity:** Low
**Area:** Backend Security
**Evidence:** `backend/server/src/handlers/admin/modules.rs:123-161` — no icon validation in `update_module` handler or service.

**Recommended fix:**
- Define the approved icon list in a shared location (e.g., `rustshare_core::domain::icons`)
- Validate `input.icon` in `ModuleService::update_module` against the approved list
- Return `ModuleError::InvalidData("Unknown icon")` for rejected values
