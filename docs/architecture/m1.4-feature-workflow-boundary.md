# M1.4 feature workflow boundary

Issue #287 starts with the authenticated `GET /api/v1/features` read. The feature response and route stay unchanged.

## Dependency path

Before:

```text
HTTP handler -> DatabaseState/PgPool -> SQLx query -> PostgreSQL workflows
```

After:

```text
HTTP handler -> DatabaseState -> WorkflowRepository -> SQLx -> PostgreSQL workflows
```

`DatabaseState` injects the repository; it contains the workflow SQL and returns only a boolean. The handler keeps authentication extraction, response mapping, and `AppError` conversion. No feature-state cache is introduced.

## Tenant behavior

The current query matches `key = 'invite_email' AND status = 'active'` without a `tenant_id` predicate. The workflow schema has a `tenant_id` column and a `(tenant_id, key)` uniqueness constraint; its seed inserts the invite workflow in the nil/system tenant. The admin workflow and invite paths also find this workflow by key without a tenant predicate. This establishes an installation-wide behavior in the current code, but does not prove that this is the intended long-term tenancy model. This change preserves the existing predicate exactly. The authenticated HTTP regression places the workflow in a different tenant from the caller and confirms the existing global result. Changing its scope requires a separate security review.

## SQL-in-handler guard

`scripts/handler-sql-baseline.json` records sorted fingerprints of SQL construction and execution sites in each handler module, including inline test modules. `scripts/check_handler_sql.py` rejects new or changed sites and requires an explicit baseline update when a reviewed site is removed. Its negative fixture and independently tested syntax cases cover qualified paths, chained imports, aliases, raw identifiers, macro delimiters, lifetimes, `raw_sql`, `QueryBuilder`, and Executor calls with SQL stored in variables. Nested comments and quoted/raw/byte strings are excluded from code detection.

Execution method names (`execute`, `fetch*`, `prepare*`, `describe`) are conservatively reserved in handlers, because source scanning cannot infer the receiver type or whether an argument variable holds SQL. The baseline includes one non-SQL exception: `source_authorizer.fetch` in `chat_resource.rs`. New non-SQL uses of reserved names require an explicit baseline review. The guard does not expand custom macros or resolve APIs re-exported by other crates; code review remains necessary for those cases. A compiler lint is the next step if generated SQL enters handlers.

The corrected inventory has 295 query-construction sites in 29 modules and 296 execution sites in 30 modules (591 fingerprints total). Construction and execution are counted separately even when they belong to the same query chain. The earlier 258-site inventory missed 45 real constructions and falsely classified eight unrelated constructors as `QueryBuilder`. No handler SQL was added while correcting this inventory. The baseline remains temporary debt; each moved family should reduce it.
