# M1.4 feature workflow boundary

Issue #287 starts with the authenticated `GET /api/v1/features` read. The feature response and route stay unchanged.

## Dependency path

Before:

```text
HTTP handler -> DatabaseState/PgPool -> SQLx query -> PostgreSQL workflows
```

After:

```text
HTTP handler -> DatabaseState/PgPool -> WorkflowRepository -> SQLx -> PostgreSQL workflows
```

The repository contains the workflow SQL and returns only a boolean. The handler keeps authentication extraction, response mapping, and `AppError` conversion. No feature-state cache is introduced.

## Tenant behavior

The current query matches `key = 'invite_email' AND status = 'active'` without a `tenant_id` predicate. The workflow schema has a `tenant_id` column and a `(tenant_id, key)` uniqueness constraint; its seed inserts the invite workflow in the nil/system tenant. The admin workflow and invite paths also find this workflow by key without a tenant predicate. This establishes an installation-wide behavior in the current code, but does not prove that this is the intended long-term tenancy model. This change preserves the existing predicate exactly. Changing its scope requires a separate security review.

## SQL-in-handler guard

`scripts/handler-sql-baseline.json` records the number of direct SQLx query calls per handler module on the M1.4 baseline. `scripts/check_handler_sql.py` fails when a handler adds calls above that reviewed baseline, including imported or aliased query functions. Its checked-in negative fixture proves both qualified and aliased query calls in a new handler module are rejected. The baseline is temporary debt, not permission to add queries; each moved family should lower it. This count-based guard does not detect replacing an existing call in place, so review remains necessary.
