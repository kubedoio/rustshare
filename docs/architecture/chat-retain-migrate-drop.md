# Chat retain, migrate, or drop inventory

This is a non-destructive planning record for #309. It does not authorize a cutover, identity rewrite, archive, export or deletion. Keep the currently deployed Buzz authority and its data until product owners accept parity, backup/restore and per-tenant cutover evidence.

## Current implementation inventory

The current Elembra Chat path uses the pinned Buzz relay as the authoritative event/history system. Elembra observes and projects supported events for application views, search, Memory references and audit. Browser-held identity remains a separate gated path; managed identity/publishing and legacy identity replacement have independent gates (#215, #323, #424, #442, #458, #460). Files attachments are references to Files resources and must be reopened through current Files authorization. Memory Chat records are derived projections, not a second authoritative message store.

Inventory each live deployment before a migration decision. Repository inspection alone cannot prove production state:

- [ ] Buzz source/revision, relay image digest, configuration, communities and external integrations.
- [ ] Elembra Chat APIs, browser workflows, permissions, channel membership, threading, replies, reactions, deletion/moderation and current error behavior.
- [ ] Tenant/workspace/community bindings, principals, browser identity keys, identity generations and any legacy mappings. Never modify production mappings during inventory.
- [ ] Event history: message IDs, authors, timestamps, signatures, references, edits/deletions and retention behavior.
- [ ] Attachments and Files ResourceRefs; verify object ownership and current reauthorization on open.
- [ ] Search and Memory projection schemas, outbox/worker consumers, cursors, receipts and reconciliation/rebuild procedures.
- [ ] API contracts, frontend routes, callbacks, webhooks, scheduled/background processes, secrets and backup/restore dependencies.
- [ ] Export available formats, completeness, event-signature preservation, encryption/secret boundaries and restore test status.

Option C is an existing separate product, not a greenfield proposal. ## Migration sequence if later authorized

1. Inventory each deployment and produce counts/checksums without changing data.
2. Define retained user-visible behavior and approved identity/workspace mapping.
3. Implement a disposable export/import proof; preserve source event IDs, signatures, authorship and references as provenance. Do not claim a migrated or bridged record has the original user's signature unless the original signed event is retained byte-for-byte.
4. Restore and compare migrated history, attachments, authorization, search and Memory projections.
5. Rehearse per-tenant cutover and rollback with no production identities.
6. Obtain product-owner and independent security approval for one tenant at a time.
7. Keep the old authority read-only and recoverable through the agreed rollback window; retire only after acceptance.

Until then, retain existing functionality and data. Do not run two authoritative Chat backends, mutate production mappings, archive legacy data or implement H4 cutover code.

## H4 architecture recommendation (2026-11-26)

Architecture source snapshot: RustShare protected main `af8f695b66b14526be1eff0b027b353f807dce38`; external RustChat main `b195719d40212fbfba227ce9266ac2420572860c` (verified 2026-11-26). The tracked Elembra Chat app uses Buzz as its signed message/history authority and depends on fork-specific signed authorization, state and channel APIs. `config/buzz-compatibility.env` pins Buzz source `b3aaabf635d992b08b57773071686a92196884e1` and image `ghcr.io/kubedoio/buzz-elembra@sha256:38c362bb37d15ea879634b0f56a867401df4e4e0074a84382dff6b07bb578b4e`; `docker-compose.alpha.yml` selects `RUSTSHARE_CHAT_AUTHORITY=buzz`. The web client in `frontend/src/lib/chat/` implements the current fork's NIP-29 channel, NIP-10 thread, NIP-25 reaction and deletion/moderation flows. `backend/server/src/buzz_gateway.rs` uses signed NIP-98 requests and pinned signed relay responses for access/state operations.

The separate [RustChat repository at the inspected commit](https://github.com/kubedoio/rustchat/tree/b195719d40212fbfba227ce9266ac2420572860c) contains a Rust/Axum and PostgreSQL authority, Vue client, REST/WebSocket APIs, RustChat organizations/teams/memberships, posts/threads/reactions, files, calls, search, administration and OIDC. It also includes AI-agent and knowledge-base/RAG subsystems; these have not been qualified against Elembra Memory's source-authorization boundary. Its [ADR-005](https://github.com/kubedoio/rustchat/blob/b195719d40212fbfba227ce9266ac2420572860c/docs/adr/ADR-005-rustchat-core-and-buzz-integration.md) keeps Buzz optional; its [Buzz contract](https://github.com/kubedoio/rustchat/blob/b195719d40212fbfba227ce9266ac2420572860c/docs/integrations/buzz.md) is outbound-only and bridge-key signed. This makes C a developed alternative, but not a qualified Elembra drop-in: Elembra principal/tenant binding, Files/Memory source authorization, per-user Buzz identity/provenance, bidirectional history, and live deployment/data mapping are unproven. Repository code does not prove whether RustChat has deployed data. #309 still requires a non-destructive, deployment-level inventory of live RustChat instances, data, identities, backups, external clients and rollback dependencies.

ADR-0044 records the owner's strategic choice of **A: managed Elembra identities on unmodified upstream Buzz** and authorizes isolated Phase 2A planning. ADR-0046 records the same owner-selected Option A for managed NIP-29 publishing. These decisions do not authorize managed Chat enablement, release or migration. RustChat ADR-005 separately makes the RustChat product its own authority with Buzz optional; it does not change RustShare ADR-0044 or authorize switching Elembra to RustChat. The actual supported Elembra deployment remains fork-backed (B), so the current operating posture is D: preserve it with bounded maintenance while A's independent security, upstream-compatibility and release gates remain open. No A-versus-D owner choice is pending. C is not recommended on current evidence; evaluate it separately only if the owner explicitly reopens the accepted A target.

**Recommendation and decision status:** Option A is the owner-approved strategic target in ADR-0044 and ADR-0046. Option D is the current operating posture: preserve the supported fork-backed deployment with bounded B-style security/compatibility maintenance until independent security, desktop, upstream-fix, recovery and migration gates pass. No A-versus-D owner choice is pending; C is not recommended on current evidence and should receive a separate evaluation only if the owner explicitly reopens A. B maintenance is limited to security and compatibility fixes, pinned artifacts and regression/conformance checks; avoid new fork-only product surface. RustChat ADR-005 is a separate product decision and does not amend RustShare ADR-0044. The exact protected-main install/upgrade/restore/rollback pass is recorded in [the af8f695b candidate evidence bundle](../pilot/evidence/candidate-af8f695b-disposable-pilot-2026-11-26.md); exact-main Integration Tests run [45762572054](https://github.com/kubedoio/rustshare/actions/runs/45762572054) also passed, including Chat Product Acceptance. These results do not establish stock-desktop acceptance, independent security acceptance, publisher remediation, or migration authorization. Keep #309's live deployment/data/backup inventory as a hard gate. This recommendation authorizes no implementation, managed identity/signing, production mapping changes, migration or data removal. Chat migration remains **BLOCKED** pending its explicit gates.
